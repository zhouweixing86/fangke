## 1. 通讯与签名

| 项 | 规则 |
|---|---|
| 协议 | HTTP **POST**，`Content-Type: application/json`，UTF-8 |
| 统一地址 | `/thirdServer/v1/openApi`（**所有接口同一个 URL**，靠 `service_name` 区分） |
| 鉴权 | 每个请求带 `sign`；`secretKey` 由车场平台分配，**每个车场不一样** |
| 签名步骤 | ① 取所有**非空**参数（`null`、空串、文件类型不参与），按参数名 ASCII 升序拼成 `k1=v1&k2=v2`；② 末尾追加 `&key=<secretKey>`；③ 整串做 **MD5 → 32 位大写** 即 `sign` |
| 特例 | 月卡接口（3.8）的 `data` 数组**不参与签名**；所有 `sign` 字段本身不参与 |
| 判定 | 返回 `code=1` 成功、`code=0` 失败（`msg` 为原因） |

Java 参考实现（厂商文档原文逻辑，已在本项目 `CloudParkingSign` 里实现并有单测）：

```java
String[] keys = data.keySet().toArray(new String[0]);
Arrays.sort(keys);
StringBuilder sb = new StringBuilder();
for (String k : keys) {
    if ("sign".equals(k) || "data".equals(k)) continue;      // sign/data 不参与
    String v = data.get(k);
    if (v != null && !v.trim().isEmpty()) sb.append(k).append('=').append(v.trim()).append('&');
}
sb.append("key=").append(secretKey);
String sign = MD5(sb.toString()).toUpperCase();
```

## 2. 我方要用的接口

### 2.1 `visitor_sync` —— 车辆访客预约（**核心：访客车牌下发**）

平台 → 车场。**按车牌**增/改/删访客车辆白名单，带生效时间段。

| 参数 | 必选 | 类型 | 说明 |
|---|---|---|---|
| service_name | 是 | string | 固定 `visitor_sync` |
| park_id | 是 | string | 车场编号 |
| sign | 是 | string | 签名 |
| visitor_id | 是 | string | **访客唯一编号**（改/删按它定位；我方用 `plateNumber` 派生，保证稳定） |
| plateNumber | 是 | string | 车牌号 |
| beginTime | 是 | string | 生效开始 `yyyy-MM-dd HH:mm:ss` |
| endTime | 是 | string | 生效结束 |
| personName | 是 | string | 姓名 |
| mobile | 否 | string | 手机号 |
| type | 是 | int | 二维码类型：`1` 入口登记码（需 `channel_id`）/ `0` 访客预约码 |
| channel_id | 否 | int | 通道编号；`type=1` 时必传 |
| passCount | 否 | int | 通道次数权限 |
| operate_type | 是 | int | **1 添加 / 2 修改 / 3 删除** |
| remark | 否 | string | 备注 |
| createTime | 是 | string | 操作时间 |
| reservedStr | 否 | string | 原样返回，可用于放我方单号 |

返回：`service_name`、`park_id`、`visitor_id`、`code`、`msg`、`reservedStr`。

### 2.2 `downBlackCar` —— 下发黑名单

| 参数 | 必选 | 说明 |
|---|---|---|
| service_name | 是 | 固定 `downBlackCar` |
| park_id / sign | 是 | |
| plateNumber | 是 | 车牌 |
| remark | 是 | 备注 |
| black_uuid | 是 | 黑名单唯一编号（改/删按它） |
| opType | 是 | 1 新增 / 2 修改 / 3 删除 |
| beginTime / endTime | 是 | 生效区间 |
| createName / createTime | 是 | 操作人/时间 |

> 我们平台的「车辆黑名单」目前挂在 `blacklist` 表（按人/证件），车牌黑名单未单独建模。若要做，需要先加「车牌黑名单」数据源。

### 2.3 `query_channels` —— 查询通道列表

入参：`service_name=query_channels`、`sign`、`park_id`。
出参 `data[]`：`channelId`、`channelName`、`channelType`（**1 进 / 2 出**）、`cameraIP`、`deviceSN`、`deviceStatus`、`thirdNumber`。

> 现场「出口车闸」的 `channelId` 必须从这里查出来填到配置里（`visitor_sync` 的 `type=1` 时要用）。

### 2.4 员工长期车牌：`visitor_sync` 还是 `month_dataSync`？

| 方案 | 接口 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐先试）** | `visitor_sync`，`endTime` 给到期日/2099-12-31 | 与访客同一套逻辑、字段少 | 车场侧可能按「访客」计费/限制时长 |
| B | `month_dataSync`（3.8 第三方同步月卡） | 车场视为月卡/贵宾车，长期有效 | 必填 `authType`/`receiveMoney`/`factMoney`/`personSpaceNum` 等收费字段，需先 `query_authTypes` 拿车辆类型 |

> **需要车场方确认**：员工车牌走 A 是否可行；不行就按 B 实现（我方 `receiveMoney=factMoney=0`、`personSpaceNum=1`，`authType` 取车场给出的「员工/月卡」类型）。

### 2.5 车场回调我们（进场/出场/是否开闸）

| 回调 | service_name | 用途 | 我方现状 |
|---|---|---|---|
| 车辆入场 | `inpark` | 车牌/时间/通道/图片 | 已有 `/openapi/v1/vehicleEvent` 通用入口，需要按此字段做适配 |
| 车辆出场 | `outpark` | 出场 + 费用明细 | 同上 |
| 场内改车牌 | `opPlate` | 车场本地改/删车牌 | 未接 |
| **是否开闸** | `checkOpenGate` | 车牌识别后问我们「放不放」：返回 `code` 0 允许 / 1 不允许 / 2 自行处理 | 未接，**这是「车牌不在白名单也能按平台规则放行」的关键** |

`checkOpenGate` 入参：`park_id`、`plateNumber`、`inoutType`(1 进 2 出)、`inoutParkTime`、`inoutParkChannelNumber`、`inoutParkChannelName`。

## 3. 平台侧设计（本次落地）

```
员工档案 plate_no ─┐
                  ├─► VehiclePlateService.snapshot()（去重、员工优先）
访客预约 plate_no ─┘            │
                                ▼
                   VehiclePlateCloudService.reconcile()
                   ├─ 与 vehicle_plate_push 表比对，算出 新增/修改/删除
                   ├─ 逐条调用 visitor_sync（operate_type 1/2/3）
                   └─ 成功后落库（失败留错误，下轮重试）
                                ▲
            定时任务（默认 60s）/ 管理端「下发到车闸」按钮
```

- **数据源不新建表**：员工车牌 `employee.plate_no`（长期）、访客车牌 `appointment.plate_no`（有效期 = 预约起止，且需审批通过）。
- **幂等**：`vehicle_plate_push` 以 `plate_no` 为主键记录「已下发快照」，同一车牌内容不变就不重复调用。
- **删除**：快照里消失的车牌（预约过期/作废、员工停用）→ `operate_type=3`。
- **失败重试**：调用失败不删记录，下轮 reconcile 自动重试；连续失败在管理端可见错误信息。
- **开关**：`fangke.vehicle.cloud.enabled=false` 时只算不发（dry-run），联调前不影响现网。

### 3.1 配置项（生产 `/opt/fangke/.env`）

```yaml
fangke:
  vehicle:
    cloud:
      enabled: false                 # 拿到凭据后再开
      base-url: https://<车场平台域名>/thirdServer/v1/openApi
      park-id: ""                    # 车场编号（车场方给）
      secret: ""                     # secretKey（车场方给，每个车场不同）
      channel-id: 0                  # 出口通道编号（query_channels 查）
      type: 0                        # 0 访客预约码 / 1 入口登记码
      timeout-seconds: 8
      sync-ms: 60000                 # 定时对账间隔
```

### 3.2 管理端

- 设备管理 → 车闸相机 → 「车牌名单」：`下发到车闸` 按钮触发一次 reconcile，结果里显示 `已新增/已修改/已删除/失败`。
- 名单表格的「来源/有效期」保持现有口径；下发状态看「最近下发」列（`已同步 / 待同步 / 失败原因`）。

## 4. 需要车场方/你提供的信息（缺一不可）

| # | 资料 | 用途 | 备注 |
|---|---|---|---|
| 1 | 车场平台**接口域名/地址** | 调用 `/thirdServer/v1/openApi` | 例：`https://xxx.com`（是否内网、是否需要 IP 白名单） |
| 2 | `park_id` 车场编号 | 所有接口必填 | |
| 3 | `secretKey` 签名密钥 | 签名 | 每个车场不同，**不要发群里**，走密码渠道 |
| 4 | 出口**通道编号** `channelId` 与名称 | `visitor_sync` 的 `channel_id`/日志 | 可先用 `query_channels` 查（需已开通接口） |
| 5 | 接口是否**已付费开通** | 未开通调用会失败 | 文档首行注明「接口需要客户付费才可以调用」 |
| 6 | 员工车牌用哪种方式（§2.4 A/B） | 决定调 `visitor_sync` 还是 `month_dataSync` | 若 B，还需要「车辆类型 authType」清单（`query_authTypes`） |
| 7 | 车牌识别规则 | 新能源/黄牌/临时牌格式是否要特殊处理 | 我方统一大写、去空格/· |
| 8 | 回调地址配置 | 车场把 `inpark/outpark/checkOpenGate` 推到我们 | 需要车场在平台侧填我们的回调 URL；是否需要公网域名/HTTPS |
| 9 | 是否启用 `checkOpenGate` | 让车场「识别到车牌先问我们」 | 启用后可做到「不在名单也按规则放行/拒绝」 |
| 10 | 测试车场/测试车牌 | 联调用 | 建议给一块测试车牌，避免影响真实车辆 |

## 5. 联调顺序（拿到 1~4 后）

1. `query_channels`：确认出口 `channelId`、`deviceSN`，与现场相机对上。
2. `visitor_sync` **添加**一条测试车牌（`operate_type=1`，时间窗给 10 分钟）→ 车场后台能看到该访客车辆。
3. 进/出场实测：车场回调 `inpark/outpark` 是否能到我们（先看 nginx 日志），字段与我们 `vehicle_event` 对齐。
4. `operate_type=2` 改时间窗、`operate_type=3` 删除 → 车场侧名单同步变化。
5. 打开 `enabled=true`，观察一次「预约审批通过 → 自动下发」的完整链路。
6. 打开 `checkOpenGate`（可选），验证「未预约车辆」按规则被拒。

---

## 6. 注意

- 车场接口是**付费能力**，且 `secretKey` 每车场不同；换车场要换配置。
- `visitor_id` / `black_uuid` / `plateID` 都是「改删定位键」，必须由我方稳定生成（不能用自增 ID 之类的易变值）。
- `sign` 里 `data` 不参与（月卡批量接口），单条接口没有该例外。
- 时间一律 `yyyy-MM-dd HH:mm:ss`，按车场所在时区（默认 `Asia/Shanghai`）。
- 车场回调图片只保留 7 天，需要的图片要及时落我们自己的对象存储。
