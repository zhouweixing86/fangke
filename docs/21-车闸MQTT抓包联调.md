# 21 · 车闸 MQTT 抓包联调（现场无电脑方案）

> 背景：现场不能放电脑，云服务器直连相机又需要端口映射；改为**相机作为 MQTT 客户端连我们的云 broker**，
> 先用 broker 日志把协议报文抓出来，再按报文实现「车牌下发 + 识别结果上报」。
> 相机：`COPCM-E10-LS26050994`（PCM500FSPUTV14，固件 21.2.0.3045），`192.168.10.152`。

---

## 1. 云上 broker（已就绪）

| 项 | 值 |
|---|---|
| 服务 | Mosquitto 2.0（`systemctl status mosquitto`，监听 `0.0.0.0:1883`） |
| 账号 | `fangke` / 见 `private/腾讯云部署凭据.md` |
| 抓包服务 | `fangke-mqtt-capture`：订阅 `#`，落 `/opt/fangke/logs/mqtt-capture.log`，格式 `ISO|topic|payload` |
| 自测 | `mosquitto_pub -h 127.0.0.1 -u fangke -P ... -t test/x -m ok` → 日志出现一行 |

> ⚠️ **必须先在腾讯云轻量控制台放行 TCP 1883**（来源 `0.0.0.0/0`），否则相机连不进来。
> 当前实测公网 1883 不通，只有 22/80 开放。

## 2. 相机侧协议线索（从 Web 后台读到）

相机「平台配置」有 6 套协议，其中 **标准协议（MQTT）** 已经连着厂商平台，字段是通用的「一设备一对主题」：

| 字段 | 当前值 | 说明 |
|---|---|---|
| 平台地址 / 端口 | 加密显示 `Enc[...]` / `9883` | 厂商平台 |
| 客户端ID | `{DevSerialNum}` | 设备序列号 |
| **自定义发布主题** | `upload/{DevSerialNum}` | 相机 → 平台（识别结果、心跳） |
| **自定义订阅主题** | `download/{DevSerialNum}` | 平台 → 相机（**指令/白名单下发**） |
| Rtd 心跳 | 30 秒 | |
| 消息回执 / 离线重传 / QOS1 | 开关 | 说明协议有 ack 与重传 |

另外还有独立的 **第三方协议(MQTT)** 页签（自己的启用开关 + URL/端口/用户名/密码/客户端ID/心跳/图片上传/**白名单策略**/OSS/离线LED），
用它做抓包**不影响**现在的标准协议连接。

## 3. 抓包步骤（不改厂商平台）

1. 腾讯云放行 1883；
2. 相机「高级设置 → 平台配置 → 第三方协议(MQTT)」：
   - 启用此 MQTT：开
   - URL：`58.87.99.249`　端口：`1883`
   - 用户名：`fangke`　密码：见凭据文档
   - 客户端ID：保持 `{DevSerialNum}`
   - Rtd 心跳：5 秒（抓包阶段短一点）
   - 白名单策略：先「不启用」（避免和后面下发混淆）
   - 保存所有
3. 观察两处：
   - 相机头部是否仍显示「标准协议(MQTT) 已连接」（确认没影响厂商平台）；
   - 云上 `tail -f /opt/fangke/logs/mqtt-capture.log`：应出现相机连上后的 **心跳/在线报文**（topic 与 payload）。
4. 让一辆车经过（或用相机的「抓拍识别」按钮），日志里会出现**识别结果报文**（车牌、时间、图片地址等）。
5. 用 `mosquitto_pub` 往相机订阅的主题发一条测试指令，观察相机行为（LED/开闸），反推下发报文格式。

## 4. 抓到报文后怎么落地

| 报文 | 落点 |
|---|---|
| 心跳/在线 | 更新设备在线状态（可选） |
| 识别结果 | 解析后 POST 到现有 `/openapi/v1/vehicleEvent`（复用通行判定/入库/开闸） |
| 白名单下发 | 云平台按「员工 + 当天已授权访客」生成清单（复用 `vehicle_plate_push` 差分），publish 到相机订阅主题 |
| 回执 | 按报文里的 ack 字段处理，失败重发 |

## 5. 回滚

相机「第三方协议(MQTT)」关掉即恢复原状；标准协议(MQTT) 全程不动。
若必须临时切「标准协议(MQTT)」指向我们，记得把原 URL/端口/用户名/密码（加密串）先截图保存。

## 7. 实测记录（2026-11-25 21:55–22:05）

**防火墙**：控制台规则写成了 **1833**（应为 1883）。为不打断联调，临时让 broker 也监听 1833 适配。

**相机侧表现**（抓包 + broker 日志）：

| 阶段 | 结果 |
|---|---|
| TCP 连接 `58.87.99.249:1833` | ✅ 成功（出口 IP 走 4G：`111.55.206.122`，另有办公网 `117.89.73.58` 探测） |
| MQTT CONNECT | ✅ 标准 3.1.1：`MQTT` level 4、clean session=1、keepalive 10、clientId `COPCM-E10-LS26050994`、用户名 `fangke`、密码明文带上 |
| 认证 | ✅ broker 日志 `u'fangke'`，CONNACK 返回 `20 02 00 00`（接受） |
| **CONNACK 之后** | ❌ 相机 **约 50ms 内主动发 TCP RST**，未发 SUBSCRIBE / PUBLISH，然后每 5 秒重连一次 |

**对照实验**（排除 broker 兼容性）：

| 实验 | 结果 |
|---|---|
| Mosquitto 2.0.18 | CONNACK 后立即被 RST |
| EMQX 5.8.6 | 同上 |
| 自写 fake broker（CONNACK `session present=0`） | 同上 |
| 自写 fake broker（CONNACK `session present=1`） | 同上 |
| egress 加 150ms 延迟 | 同上 |

**结论**：不是端口、不是认证、不是 broker 兼容或时序问题；相机的「第三方协议(MQTT)」在 CONNACK 之后
**还需要某个我们不知道的应用层握手/指令**（或该通道只认厂商自己的平台）。
需要厂商提供 **《第三方协议(MQTT) 接入说明》**，或者直接问厂商：*为什么 CONNACK 后立即断开*。

## 8. 现场状态与回滚（重要）

- 相机当前处于「**第三方协议(MQTT) 未连接**」，即**已脱离厂商平台**，出口闸暂时没有平台放行能力。

## 10. 关键发现：是中间网络设备在重置 MQTT（2026-11-25 22:10）

用 `tcpdump -v` 对比 TTL：

| 包 | TTL |
|---|---|
| 相机发来的数据包（CONNECT 等） | **48** |
| 断开时的 TCP RST | **34** |

**TTL 不同 → RST 不是相机发的**，而是链路中间的设备（运营商 4G 出口的 DPI/防火墙）注入的。
相机自己的日志也印证：`连接断开, 断开原因: The connection was lost.`（不是它主动关）。

对照实验：从**办公网**（`117.89.73.58`）用 PowerShell 手写 MQTT CONNECT 连我们 `:1833`，
收到 `20 02 00 00` 后**连接保持**，没有被重置 → 办公网到服务器是通的，问题在相机的 **4G 出口**。

### 10.1 由此产生的可行路径

| 方案 | 说明 |
|---|---|
| 让相机走**内网/WiFi 出口**（不走 4G） | 办公网出口 MQTT 实测可通，最省事 |
| 换**端口/TLS**（443、8883） | 若 DPI 按端口/协议识别，TLS 可绕过；需相机支持或换承载 |
| 走相机「标准协议（WEBSOCKET）」 | 该 tab 是**自家 WS 协议**（`ws://x:8866/ServerAgent` + 图片 `ServerPic`），不是 MQTT-over-WS，需要厂商文档 |
| **SDK 直连 9910** | 不依赖 MQTT，只要网络可达（端口映射/VPN），SDK 白名单已实测可用 |
| **车场平台 openAPI** | 不走相机出网，只要凭据 |

### 10.2 额外发现：相机有 HTTP/XML 控制接口（可用于远程调试）

Web 后台的所有操作都走 `POST http://<ip>/Signalway.fcgi?<Cmd>`，请求体是
`XML[Value]=<HvCmd ver="3.0"><CmdName ...>...</CmdName></HvCmd>`，返回 `HvCmdRespond`。
已确认可用命令（举例）：

| 命令 | 作用 |
|---|---|
| `DownloadINIFileEx` | 返回 `RetMsg="ini/192.168.10.152_MQTT.ini"`，再 `GET /ini/<文件名>` 就能下载 MQTT 配置 INI |
| `GetRunStatus` / `GetMqttRunStatus` | 运行状态 / MQTT 连接状态（返回"未连接"等） |
| `OptResetMode` | 复位模式 |

我们甚至用「上传配置」把 `EnableMqttDebugMsg` 从 0 改成 1，让相机把 MQTT 库 debug 写进日志。
**如果相机网络可达，这条路可以做远程配置/巡检**（不用依赖厂商 App）。

## 11. 结论（回答"是不是只缺文档"）

不是只缺文档。当前卡点有两层：
1. **链路层**：相机 4G 出口的中间设备会重置 MQTT（TTL 证据），换网络或换承载才可能通；
2. **协议层**：第三方协议/WS 协议的报文与握手细节未知，需要厂商文档或支持。

所以要么**换一条能通的链路**（内网出口 / 443+TLS / 端口映射走 SDK / 车场平台），
要么**拿到厂商协议文档 + 确认相机固件支持该链路**。
