# 17 · 设备接入配置手册（现场实施版）

> 适用：YC-P208 / RV1109 系列人脸识别终端，走 **HTTP 查询式（客户端版）协议**。
> 目标：设备到手 → 上电联网 → 接到访客平台 → 名单下发 → 刷脸/刷身份证能开门。
> 协议实现细节见 [14-设备协议-新终端HTTP轮询版](./14-设备协议-新终端HTTP轮询版.md)，本文只讲**怎么操作**。

---

## 0. 开箱前先备齐这 5 个数

| 项 | 示例（本机联调实际值） | 说明 |
|---|---|---|
| 平台地址 | `http://192.168.0.103:8080` | **只填根地址**，不要带 `/openapi/v1` |
| 平台 Key | `fangke-pull-key` | 与平台 `fangke.device.pull-sign-key` 一致 |
| 设备 IP | `192.168.0.104` | 路由器里查，或设备后台「系统信息」看 |
| 设备后台密码 | `admin` / `888888` | 出厂默认 |
| 平台账号 | `admin` / `Admin@123456` | 平台管理端登录 |

平台侧要保证：8080 端口对局域网开放（Windows 需加防火墙入站规则），且 `GET /health` 能返回 `{"code":0,...}`。

---

## 1. 上电 + 联网

1. 接 12V 电源，等机器开机到待机画面。
2. **优先插网线**。WiFi 实测不可靠：信号强度显示为空、有时需要重启 WiFi 模块才连上；本机就是插网线后才稳定。
3. 若要 WiFi：只能连 **2.4G** 频段，且路由器不要开启"双频合一自动优选"。
4. 建议配 **静态 IP**（设备后台 → 网络设置），避免 DHCP 换地址后要重新找设备。

设备后台 → 基础设置 → **网络设置**，填：IP / 网关 / 子网掩码 / DNS（示例 `192.168.0.104` / `192.168.0.1` / `255.255.255.0` / `223.5.5.5`）。

验证联网：从平台这台电脑 `ping 设备IP`（设备可能禁 ICMP，ping 不通不代表没连上），**更可靠的做法**是用浏览器打开 `http://设备IP/home.html`，能出登录页就说明二层通了。

---

## 2. 登录设备后台

浏览器打开 `http://设备IP/home.html`，账号 `admin`，密码 `888888`（本机已改过则为实际密码）。

> 部分固件 80 和 9090 端口都是同一套后台，随便哪个都行。

---

## 3. 配置「第三方设备管理平台-HTTP」（**关键一步**）

左侧菜单 → 基础设置 → **平台管理** → 顶部页签 **第三方设备管理平台-HTTP**，按下面四项填：

| 界面字段 | 配置项 | 填什么 | 常见错误 |
|---|---|---|---|
| 启用第三方平台 | `thirdcloudflag` | **启用** | 忘开 → 设备一直不发心跳 |
| 第三方平台地址 | `thirdupdateurl` | `http://平台IP:8080` | ❌ 填成 `http://平台IP:8080/openapi/v1` → 设备会再拼一次，变成 `/openapi/v1/openapi/v1/heartBeat`，平台返回 404，设备判定故障后停发心跳 |
| 第三方平台Key | `thirdupdatekey` | 与平台 `pull-sign-key` 一致 | 联调期平台设 `fangke.device.pull-verify-sign=false` 可跳过校验 |
| 设备开机是否同步名单 | `thirdcloudsynclist` | **启用** | 不启用则开机不自动拉全量名单 |

最后点右下角 **保存设置**，提示 `set connect Cloud success` 即为成功（HTTP 200 + `result: 0`）。

> 页签里的「第三方平台记录上传」（`updaterecord` / `hearturl` / `updateurl`）属于另一套**回调式**协议，本项目不用，留空即可。

---

## 4. 重启设备（必做）

心跳线程**只在开机和保存配置时重建**，改完配置不重启，设备可能仍然按老地址发（或干脆不发）。

三种重启方式，任选：

1. 设备后台 → 系统信息 → 系统设置 → **设备重启**；
2. 直接断电重上电；
3. 脚本：`POST http://设备IP/setDeviceReboot`，body `{"token":"<登录返回的 token>"}`。

重启后约 60~90 秒可再次访问后台。

## 5. 平台侧：确认设备自动登记并分配门点

设备第一次心跳会**自动登记**到「待分配」门点，平台日志会打印：

```
自动登记查询式终端 deviceNo=2608252243655 ip=192.168.0.104，已放入「待分配」…
```

平台管理端 → 设备管理，找到这台设备（SN 是**协议编号**，不是机身标签 SN），点编辑：

- 设备名称：`园区大门-人脸终端1`
- 型号：`YC-P208`
- 所属门点：选真实门点（如「园区大门」）→ **必须选**，否则该门点的名单不会推给它
- 备注：写清机身标签 SN，换机时才认得出来

> 若设备只在「待分配」不动：说明心跳没到平台，回第 3 步查地址，再看平台 access log 有没有请求进来。

## 6. 建档 + 下发名单

1. 平台管理端 → 组织与员工 → 新建员工（姓名、工号、部门、手机号、**身份证号**）。
2. 员工详情 → 上传人脸照片：
   - 支持 JPG/PNG，**≤2MB**（超过 2MB 自动压缩）；分辨率不低于 **400×400**，过大自动缩放，不用手动裁
   - 也有拖拽区：把照片直接拖进去即可
   - 超出范围会直接报错，先用看图工具裁一下（本机把 1773×2364/1MB 的证件照压到 1080×1440/116KB 才通过）；
   - 上传成功会自动触发一次下发，不需要手动同步。
3. 也可以点「一键全量同步」把所有在岗员工推一遍。

## 7. 验收：看到这 5 行就说明通了

平台 `logs/access.log`（Tomcat 全量访问日志，含 404/500）：

```
设备IP POST /openapi/v1/heartBeat         200      ← 心跳，正常 5 秒一次
设备IP POST /openapi/v1/addDevicWhiteInfo 200      ← 带名单批次（有名单变更时才出现）
设备IP POST /openapi/v1/getDevicWhiteInfo 200 15xxxx  ← 取单人详情，带 base64 照片
设备IP POST /openapi/v1/syncWhiteResult   200      ← 设备回执（resultcode=0 成功）
设备IP POST /openapi/v1/heartBeat         200 76   ← 无指令时空转
```

设备侧核对：设备后台 → 系统信息，`本地人数（curCount）` 应该等于平台下发的人数；
或直接到机器上刷脸 / 刷身份证，能开门即最终通过。

## 8. 常见问题对照表

| 现象 | 原因 | 处理 |
|---|---|---|
| 平台日志完全没有设备请求 | 设备没联网 / 地址填错 / 防火墙拦了 | 手机浏览器打开 `http://平台IP:8080/health`，能通说明平台侧没问题；再查设备地址 |
| 请求打到 `/openapi/v1/openapi/v1/...` 且 404 | 平台地址多填了 `/openapi/v1` | 改成只填根地址，保存后**重启设备** |
| 设备只发了 6 次心跳就没动静 | 那 6 次都失败（4xx/5xx），设备进入冷却 | 先修好平台/地址，再重启设备 |
| 心跳正常但不发名单 | 设备未分配门点 / 门点下没有授权 | 设备管理里分配到真实门点，再点「同步」 |
| `5003 对象存储未配置` | 平台没配 MinIO/OSS 的 AK/SK | 配置 `S3_ACCESS_KEY` / `S3_SECRET_KEY` 后重启平台 |
| 上传照片报分辨率/体积错误 | 照片太小（<400×400）或格式不支持 | 换一张清晰的正面照；**2MB 以内直接传，超过会自动压缩**，无需手动裁尺寸 |
| 刷脸/刷身份证提示「已过期」 | 平台下发的有效期超出设备 32 位时间戳范围（曾用 `9999-12-31` 表示永久） | 代码已截断到 `2037-12-31`；若再出现，查 `access_grant.valid_from/valid_to` 是否越界 |
| 刷脸不开门 | 照片没下发成功 / 人脸质量差 | 看 `syncWhiteResult` 是否成功、设备 `curCount` 是否加 1；换一张正脸照 |
| 刷身份证不开门 | 该人没有身份证号，或不在有效期内 | 员工档案补身份证号；检查 `validFrom`~`validTo` |
| 平台设备列表显示「人数 0」但设备上有 1 人 | 平台侧人数是估算值，真机以设备 `curCount` 为准 | 目前已知限制，见 §10 |
| 扫码提示「二维码未授权」 | 设备 `thirdQrUrl` 为空，只在本地判定，没来问平台 | 远程管理 →「应用二维码核验地址」；详见 §12.9 |

## 9. 换一台新机器 / 到真实现场，只需要改两处

1. 设备后台：**第三方平台地址** 改成现场平台地址（`http://现场平台IP:8080`）；
2. 设备后台：**第三方平台Key** 改成现场平台的 `pull-sign-key`。

其余（门点、名单、授权）都在平台上操作，不用碰设备。

## 11. 设备管理：远程管理 / 本地管理

设备（YC-P208）同时暴露**两个方向**的能力，界面上把它们拆开，避免"点了没反应"分不清原因：

| 分类 | 谁连谁 | 前提 | 代表能力 |
|---|---|---|---|
| **主链路（平台被动）** | 设备 → 平台 | 设备能出网（云端部署也能用） | 名单下发、远程开门（队列）、通行记录 |
| **远程管理（平台主动）** | 平台 → 设备 `9090` | **平台与设备同网**（云端一般不通） | 读参数、校时、抓拍、弹框、重启、闸机常开、恢复出厂 |
| **本地管理（跳转）** | 浏览器 → 设备 `9090` | 操作电脑与设备同网 | 设备自己的 Web 后台（`http://设备IP:9090/home.html`，admin / 设备密码） |

> 云端部署时「远程管理」连不通是**正常现象**，界面会直接提示原因并引导走「本地管理」。

### 11.1 设备下行接口全清单（厂商文档 item 231）

平台已封装的能力（`/api/admin/device/{id}/remote/*`）：

| 平台接口 | 设备接口 | 用途 | 风险 |
|---|---|---|---|
| `GET /info` | `getDeviceVersion` | 型号/固件/本地人数/运行时长/信号 | 只读 |
| `GET /parameters` | `getDeviceParameter` | 全部参数（音量、识别模式、时间组…） | 只读 |
| `GET /time` | `getDeviceTime` | 设备时间 vs 平台时间 | 只读 |
| `POST /open` | `setDeviceRemoteOpen` | **立即**开闸（秒级，不等心跳） | 会开门 |
| `POST /sync-time` | `setDeviceTime` | 校时 | 低 |
| `POST /tip` | `setShowTipMsg` | 屏幕弹框 + 语音 | 低 |
| `POST /snapshot` | `getDeviceSnapPicture` | 抓拍现场画面 | 低 |
| `POST /gate-hold` | `setDeviceOpenTime` | 闸机常开 N 分钟 | 会放开通行 |
| `GET/POST /switches` | `setDeviceParameter`（白名单键） | 摄像头扫码 / 二维码开门 / 密码开门 三个开关；访客二维码进闸必须先开「摄像头扫码」 | 低（仅白名单键，其余参数直接拒绝） |
| `POST /reboot` | `setDeviceReboot` | 重启设备 | 离线约 1 分钟 |
| `POST /restore` | `restoreDeviceDefaultParameter` | 恢复出厂参数 | **危险**：会清掉平台地址与 Key |

设备还有、但平台**未封装**的接口及原因：

| 设备接口 | 能力 | 为什么不做 |
|---|---|---|
| `setDeviceParameter` | 改参数 | 参数有 100+ 项，误改会失联；现场用「本地管理」改更直观。**例外**：三个安全开关（摄像头扫码/二维码开门/密码开门）已通过 `/remote/switches` 白名单开放 |
| `setDeviceNetwork` | 改 IP | 改错就再也连不上，必须到机器旁边操作 |
| `uploadUpgradeAPKFile` | 固件升级 | 需要先有厂商固件包与回滚方案 |
| `addDeviceAdvertPicture` / `deleteAllDeviceAdvertPicture` | 广告图 | 本业务用不到 |
| `addDeviceWhiteList` / `deleteDeviceWhiteList` / `deleteDeviceAllWhiteList` / `getAllDeviceIdWhiteList` / `getDeviceWhiteListDetailByIdNum` | 设备侧名单直改 | **会绕过业务**（授权、有效期、审计都在平台侧）；平台已用 `openapi/v1` 那套走正规链路 |
| `getPictureFeature` | 提取人像特征值 | 本业务不做特征比对，直接下发图片 |
| `getDeviceSnapFace` | 进入抓拍人脸模式 | 调试用，非必要 |
| `setAutoRebootDevice` | 定时重启 | 设备本地已有"定时重启"配置 |

### 11.2 远程开门的两条路（别混）

| 方式 | 接口 | 延迟 | 前提 |
|---|---|---|---|
| 队列开门 | `POST /api/admin/device/{id}/door/open` | ≤ 一个心跳周期（现 5 秒） | 设备能来平台拉指令 |
| 直连开门 | `POST /api/admin/device/{id}/remote/open` | 秒级 | 平台能连设备 9090 |

云端部署时只能用前者；现场调试建议用后者，立即可见。

### 12.8 实测结论：本机固件**不支持** `usertype=visitor`

厂商文档（item 231）写 `usertype` 支持 `white` / `black` / `visitor`，并说明"访客名单每 5 分钟检查一次，过期删除"。但我们按 `visitor` 下发后实测（2026-11-21，固件 `2.2.122.B61030001R`）：

| 下发类型 | 设备 `getDeviceWhiteListDetailByIdNum` 回读 | 白名单列表 | 结果 |
|---|---|---|---|
| `white` | `usertype=white` | ✅ 在册 | 可正常通行 |
| `visitor` | `usertype=black` | ❌ 不在册 | **访客会被当黑名单拒绝** |

即固件把无法识别的 `visitor` 落成了黑名单类型。**因此访客仍按 `white` 下发**，员工与访客的区分靠：

- `company` = `访客系统`
- `department` = `访客`
- `name` = 访客姓名

设备后台「用户列表」里这三列能直接区分员工与访客（见用户截图）。

配置项已改为可切换，等厂商确认合法值后无需改代码：

```yaml
fangke:
  device:
    visitor-user-type: white   # white(默认/实测可用) | visitor(文档支持但本机固件不可用)
```

> 待厂商确认：该固件 `usertype` 是否只支持 white/black，或者访客类型需要额外的字段（如 `userType` 数值枚举）。
> 在确认前**不要**把 `DEVICE_VISITOR_USER_TYPE` 改成 `visitor`，否则访客会被拒。

### 12.9 实测结论：扫码提示「二维码未授权」= 设备没配 `thirdQrUrl`

现场扫小程序生成的码，设备屏幕上直接显示「二维码未授权」，而平台侧 `access.log` **一条 `/openapi/v1/qrCodePush` 都没有**。
逐项核对设备参数后定位到根因：

| 参数 | 出错时的值 | 正确值 | 说明 |
|---|---|---|---|
| `thirdQrUrl` | **空** | `http://<平台IP>:8080/openapi/v1/qrCodePush` | 空 = 设备只在**本地**解析二维码，解析不了就直接报「未授权」，不会来问平台 |
| `thirdOpenDoorLocal` | `0` | `0` | 二维码交平台判定 |
| `QROpenEnable` | `1` | `1` | 二维码开门总开关 |
| `videoScanQRcode` | `1` | `1` | 摄像头扫码 |

**平台会写这个值的地方只有一处**：设备来拉参数（`/openapi/v1/syncDeviceParameter`）时返回
`thirdQrUrl = fangke.device.pull-public-base-url + /openapi/v1/qrCodePush`。
设备不主动拉参数，这个值就一直是空的 —— 这就是「白名单、开关全对，扫码却未授权」的原因。

#### 现在怎么配（两种都行，建议都做）

1. **管理端点一下**：设备管理 → 远程管理 → 「二维码核验接线」→ **应用二维码核验地址**
   - 同网时直连 9090 立即写入（`Set Device Parameter Success`）
   - 同时排一次参数下发，平台连不到设备时（云端部署）设备下次心跳拉参数也会自己写上
2. **自动**：审批通过并**勾选同意二维码开门**时，平台会自动给所有在用设备排一次参数下发，现场不用手工配

#### 平台侧已验证（2026-11-21，模拟设备推送同样报文）

| 设备送码写法 | 平台返回 |
|---|---|
| `{"deviceno":"2608252243655","data":{"qrCode":"RV1...."}}` | `resultcode=1 openGate=1` |
| `{"deviceno":"...","data":"RV1...."}`（data 是纯文本） | `resultcode=1 openGate=1` |
| `{"deviceno":"...","qrCode":"RV1...."}`（顶层字段） | `resultcode=1 openGate=1` |
| 拒绝场景（过期/撤销/未同意/门点不符） | `resultcode=0 openGate=0` + 中文原因 |

> 送码字段已做兼容：`data.qrCode`、`data` 内再套 JSON、`data` 纯文本、顶层 `qrCode`/`code`、
> 整个请求体就是码、`?qrCode=` 查询参数；设备号兼容 `deviceno`/`sn`/`deviceSn`。
> 平台每次收到推送都会打一行 `二维码推送 device=... code=... raw=...`，现场排查直接搜这条日志。
