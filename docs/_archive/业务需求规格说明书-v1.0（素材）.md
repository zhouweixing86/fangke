## 1. 项目概述

### 1.1 背景

客户园区现有人证核验类终端（九鼎 RV1109 系列），支持身份证读卡、人证 1:1 核验、人脸比对、二维码识别，并可通过继电器直接控制磁吸门。目前缺少统一的访客业务平台：访客无法提前预约、员工无法知晓访客到访、通道授权依赖人工、通行数据无法留痕与追溯。

本项目建设一套访客管理系统，以"谁能进、何时能进、是否进过"为核心，完成预约、审批、授权、核验、留痕的闭环。

### 1.2 建设目标

1. **访客可自助预约**：微信小程序填写信息、选择时段与门点，全程线上。
2. **审批可配置**：支持 1 级或 2 级审批，一级为被访人，二级为指定候选池中的一人。
3. **员工可代邀**：员工可为访客直接创建预约，一级审批自动通过，减少现场等待。
4. **断网可用**：网络中断时，已授权的员工与访客仍可在终端本地完成人证核验并通行。
5. **全程留痕**：每一次审批、授权、核验、通行均有记录，可追溯、可取证。
6. **管理可视化**：设备状态、名单一致性、审批时延、通行流水可查可统计。

### 1.3 建设范围

**范围内**

- 访客预约（小程序 / H5）、审批（1~2 级）、员工代邀、现场登记
- 凭证（二维码）签发、在线校验、撤销
- 员工人脸底库：导入、采集、审核、下发
- 设备接入：登录鉴权、MQTT 指令下发、名单下发、对账、记录接收、参数配置
- 通行记录、签到签离、报表统计
- **单门点模型**：访客仅从公司大门进入，预约时不选择门点；员工可在全部设备通行
- 黑名单
- 通知：小程序待办 + 订阅消息 + 客服消息
- PC 端审批（uni-app 编译 H5，小程序扫码登录）
- 管理后台

**范围外（本期不做）**

- 闸机、梯控、车辆道闸、访客卡管理
- 多租户 SaaS 对外销售（保留 `tenant_id` 字段但单租户运行）
- 人脸 1:N 访客通行（访客不采集人脸）
- 短信、邮件通知通道
- 与 HR / OA / 企业微信 / 钉钉对接

### 1.4 术语表

| 术语 | 说明 |
|---|---|
| 被访人 | 访客要拜访的员工，同时是一级审批人 |
| 一级审批人 | 被访人本人；手机号匹配不到员工时为「默认一级审批人」 |
| 二级审批人 | 从候选池中选出的第二级审批人 |
| 代邀 | 员工在小程序直接为访客创建预约 |
| 现场登记 | 访客未预约，到前台由工作人员录入 |
| 通行凭证 | 二维码；内容为平台签名的静态串 |
| 名单下发 | 平台将人员（含证件号/码/有效期/照片）同步到设备本地 |
| 对账 | 平台与设备实际人员列表的差异比对与修复 |
| 终审通过 | 最后一级审批通过，是名单下发的唯一触发点 |

## 3. 业务场景与流程

### 3.1 场景总览

系统有三个预约入口，最终收敛到同一套授权与下发机制：

| 入口 | 发起人 | 审批路径 | 典型耗时 |
|---|---|---|---|
| A 访客自约 | 访客 | 一级 →（二级） | 分钟~小时 |
| B 员工代邀 | 员工 | 一级自动通过 →（二级） | 分钟~小时 |
| C 现场登记 | 前台 | 一级 →（二级） | 取决于审批人响应 |

### 3.2 流程 A：访客自约

```
访客打开小程序
  → 微信授权登录（openid）
  → 填写：姓名、手机号、身份证号、被访人手机号、单位、来访事由、来访时段、（可选）同行人
  → 校验：身份证号格式与校验位、手机号格式、时段合法、门点存在
  → 提交 → 状态 submitted
  → 系统匹配：被访人手机号 → employee
       命中 → l1_approver = 该员工
       未命中 → l1_approver = 默认一级审批人（记录访客原填号码）
  → 状态 approving（level=1）
  → 一级审批
       通过 → 若配置二级 → 指定二级审批人 → approving（level=2）
              若仅一级 → approved
       驳回 → rejected
  → 二级审批
       通过 → approved
       驳回 → rejected
  → approved
  → 生成凭证 + 名单下发（priority=1）
  → 全部门点回执成功 → 状态 valid → 通知访客「已可通行」
  → 访客到访刷证 / 扫码 → 设备本地核验 → 开门 → 上传记录
  → 平台落通行记录 + 自动签到
  → 签离（再次刷证识别为出场，或前台手工签离）
  → 有效期结束 → 次日清理
```

### 3.3 流程 B：员工代邀

```
员工在小程序「邀请访客」
  → 填写：访客姓名、身份证号、来访时段、门点、（可选）手机号
  → 强制勾选：「已告知访客并取得其同意」
  → 校验：一级审批人状态有效（未离职/停用）、代邀有效期 ≤ 上限（默认 7 天）
  → 提交
  → 一级审批自动通过（auto_approved=1, channel=invite, acted_by=邀请人）
  → 若配置二级 → 二级审批
  → approved → 下发
  → 通知员工「已下发至 X 门点，访客可刷证进入」
```

**约束**：邀请人 = 被访人 = 一级审批人，因此"邀请"动作即一级审批决定。若邀请人账号已停用/离职，代邀直接拒绝。

### 3.4 流程 C：前台现场登记

```
前台录入（支持读卡器读身份证 / 手工录入）
  → 提交 → 走与流程 A 相同的审批链，priority=0（实时下发）
  → 前台页面显示实时进度：一级审批 / 二级审批 / 名单下发（逐门点）
  → 支持「一键催办」（订阅消息，每分钟最多 1 次）
  → 终审通过 → 逐门点下发 → 全绿后提示「可放行」
  → 审批人未响应 → 访客无法进入（系统不提供前台代审批）
```

### 3.5 审批规则

#### 3.5.1 节点生成

| 级别 | 审批人确定规则 |
|---|---|
| 一级 | ① 访客填写手机号匹配到员工 → 该员工；② 匹配不到 → 默认一级审批人；③ 员工代邀 → 邀请人本人（自动通过） |
| 二级 | 候选池仅 1 人 → 自动选中；候选池 > 1 人 → 一级审批通过时必须指定一人（未选不允许提交） |

#### 3.5.2 审批操作

| 操作 | 说明 |
|---|---|
| 通过 | 一级通过时若配置二级，需选择二级审批人 |
| 驳回 | 流程终止，状态 rejected，通知访客 |
| 转办 | 审批人可将任务转给其他人（记录原审批人与转办人） |
| 加签 | 审批人可增加一个临时节点（记录留痕） |

#### 3.5.3 超时与升级

| 配置项 | 默认值 | 说明 |
|---|---|---|
| 催办间隔 | 30 分钟 | 到期发一次提醒 |
| 升级阈值 | **不启用** | 客户确认只保留催办，不做自动转办 |
| 自动通过 | **不启用** | 系统不支持超时自动放行 |

> 若客户不接受"备用审批人升级"，需在需求确认单中书面确认：审批人未响应时访客无法进入。

#### 3.5.4 审批人有效性

- 一级/二级审批人离职、停用 → 新提交的预约不指派该人
- 已产生的待审批任务 → 自动转给备用审批人，并记录原因
- 代邀时若邀请人已失效 → 拒绝创建

#### 3.5.5 审批留痕

每条审批记录必须包含：级别、审批人、状态、时间、意见、渠道（mini/pc/invite/system）、是否自动通过、升级来源。

## 5. 硬件对接需求

### 5.1 设备参数基线

| 参数 | 值 | 说明 |
|---|---|---|
| `faceMode` | 1 | 启用人脸识别（员工） |
| `certificateMode` | 2 | 人证 + 白名单验证（访客） |
| `threshold` | 80（[70,100]） | 人脸 1:N 阈值，现场调优 |
| `manCardMatchThreshold` | 60（[30,100]） | 人证 1:1 阈值 |
| `recogRelay` | 1 | 识别即输出继电器 |
| `recogSpaceTime` | 2 秒 | 识别去重 |
| `closingDelay` | 3 秒 | 磁吸门通电/断电时长 |

> **员工通行方式（已确认）**：员工仅刷脸通行（`faceMode=1`，1:N 比对），不刷身份证；访客不采集人脸，仅刷证 + 人证核验。两类人群在同一台设备上并行工作，`faceMode` 与 `certificateMode` 需同时开启。
>
> ⚠️ 员工仅人脸一种方式存在运营风险：摄像头故障、逆光、戴口罩、照片质量差都会导致无法通行。
>
> **已确认的替代路径：前台远程开门（人工核验）**。由此带来两个必须接受的限制：
> 1. 远程开门依赖设备在线，**断网时该路径失效**；此时员工刷脸仍可用（本地底库），但刷脸失败即完全无法进入。
> 2. 前台需通过工牌/工号人工核对身份后再开门，属人工核验，符合"人脸不得作为唯一验证方式"的要求。
>
> **建议（可不采纳）**：零成本保留"刷身份证"作为第二条替代路径——设备已支持，只需员工随身带证件，即可覆盖断网场景。

### 5.3 协议硬约束（实现时必须遵守）

1. **二维码内容不能是纯数字，长度 ≥ 16**。
2. `throughDateFrom` / `throughDateTo` 日期格式 `yyyy-MM-dd`，**日期后需带一个空格**。
3. 模板照：平台负责压缩，**≤500K，分辨率 400×400 ~ 1080×1920**。
4. `sync_person` 每批 **10 人**，全量一次下发会阻塞设备登录接口。
5. `sync_card` 建议每批 **≤100 条**。
6. 刷卡时设备**延时约 3 秒**才上传记录。
7. 记录上传后平台必须回：`{"message":"Set access groups success","result":0}`。
8. **禁止调用 `SetCheckCode`**（写入 AES 校验码不可逆，会导致记录字段加密且无法还原）。
9. 记录上传存在两套字段（9.1 与附件二），需分别适配：`capture_status` / `resultStatus`、`capture_img` / `face_base64`、`person_id` / `employee_number`。
10. 无效字段（体温、健康码、核酸、疫苗）必须可反序列化但忽略。

## 8. 非功能需求

### 8.1 性能

| 指标 | 目标 |
|---|---|
| 在线比对 P99 | < 300ms |
| 记录上传受理 | < 200ms 返回 |
| 名单下发（单门点 100 人） | < 60 秒 |
| 后台列表查询 P95 | < 1.5s |
| 并发 | 支持 10 台设备同时在线、10 次/秒识别峰值 |

### 8.2 可用性

- 断网时：设备本地名单可用，通行不受影响
- 平台不可用时：记录在设备缓存，恢复后补传
- 数据库/缓存故障：返回"暂不可用"，不得误放行

### 8.3 安全

| 项 | 要求 |
|---|---|
| 传输 | HTTPS；MQTT over TLS |
| 设备鉴权 | dev_sno + register_no + token + IP 白名单；未注册设备拒绝并告警 |
| EMQX ACL | 每设备独立账号，只能读写自己 topic |
| 二维码 | HMAC/RSA 签名，含有效期与随机数，防猜测与重放 |
| 后台 | 密码强度、登录失败锁定、会话超时 |
| 权限 | 最小权限；数据范围按门点/部门 |
| 审计 | 关键操作不可删除、可导出 |

### 8.4 合规

依据《个人信息保护法》《人脸识别技术应用安全管理办法》（2025-06-01 施行）：

1. 人脸与身份证号属敏感个人信息，须**单独同意**，不得混入总协议。
2. **人脸识别不得作为唯一验证方式**：访客以"刷身份证 + 人证核验"为主，天然满足；员工以刷脸为主，替代方式为**前台远程开门（人工核验）**，需在员工告知书中写明该路径及断网时的限制。
3. 告知处理目的、方式、保存期限；提供查询、更正、删除渠道。
4. 数据最小化：只采集必要字段（访客不采集人脸）。
5. 员工代邀时必须取得访客同意，系统记录勾选时间与操作人。
6. 建立个人信息处理台账，保留删除记录。

> **待法务确认**：公有云存储人脸照片是否可接受，或需改为"仅存特征/仅存结果"。

### 8.5 可观测性

| 指标 | 告警阈值 |
|---|---|
| 设备离线 | > 5 分钟 |
| 名单一致性偏差 | > 0 持续 30 分钟 |
| 指令失败率 | > 10%（1 小时） |
| 设备人员数 | > 容量 80% |

## 10. 验收标准

### 10.1 功能验收用例（节选）

| # | 用例 | 预期 |
|---|---|---|
| AC-01 | 访客预约 → 一级审批通过（配置 1 级） | 状态变 approved，名单下发成功，访客可刷证进入 |
| AC-02 | 配置 2 级，一级通过未选二级审批人 | 提交被拦截并提示 |
| AC-03 | 配置 2 级，一级通过并指定二级 → 二级通过 | 全程留痕，最终 approved |
| AC-04 | 二级审批人与一级为同一人 | 二级自动跳过 |
| AC-05 | 员工代邀（配置 1 级） | 一级自动通过，直接 approved，10 秒内下发 |
| AC-06 | 员工代邀（配置 2 级） | 一级自动通过，二级待审批 |
| AC-07 | 访客填写不存在的员工手机号 | 走默认一级审批人，详情页显示原填号码 |

| AC-09 | 访客刷身份证（在名单内且在有效期） | 人证核验通过 → 开门 → 3 秒内上传记录 |

| AC-13 | **断开外网** | 已下发名单的员工与访客仍可正常通行 |
| AC-14 | 断网期间新登记访客 | 无法下发，前台提示"设备离线"，需告警 |

| AC-17 | 预约撤销 | 全部门点 `delete_person`，访客刷证被拒 |

| AC-22 | 设备断电 | 磁吸门释放（常开），恢复后设备自动重连并对账 |
| AC-23 | 员工刷脸失败（逆光/遮挡） | 前台核实工号后远程开门成功，记录操作人与时间 |

- 10 台设备同时在线，连续 24 小时无掉线
- 100 人名单全量下发在夜间窗口内完成
- 100 次连续刷证无超时

- 日志完整性：任意一次通行可在 30 秒内追溯到审批链

## 11. 风险与假设

### 11.1 风险清单

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | `certificateMode=2` 白名单按**人脸特征**匹配（而非证件号） | 访客必须采集照片，方案大改 | **W0 现场验证，最高优先级** |
| R2 | 老固件忽略有效期 | 访客名单永不过期，安全事故 | 现场验证 + 平台侧不依赖设备过期 |
| R3 | 设备无法同时支持"本地名单 + 在线比对" | 现场登记无兜底 | 现场验证；若无则依赖实时下发 |
| R4 | 订阅消息配额耗尽 | 审批无人知晓 | 待办角标为主通道；配额提示；PC 轮询 |
| R5 | 无前台代审批 | 审批人不响应时访客无法进入 | 备用审批人升级机制；或书面免责 |
| R6 | 底库被历史访客占满 | 新访客下发失败 | 每日清理 + 容量水位告警 |
| R7 | 设备时间漂移 | 有效期误判 | 每日校时 + 偏差告警 |
| R8 | 厂商文档版本混乱（9.1 重复编号、字段命名不一致） | 联调返工 | 锁定固件版本与文档版本 |
| R9 | 磁吸门断电常开、无防尾随 | 安全隐患 | 客户告知书 + 消防走强电 |
| R10 | 公有云存人脸照片的合规争议 | 项目受阻 | 提供"仅存结果不存照片"模式 |
| R11 | **员工唯一替代方式是前台远程开门** | 断网 + 刷脸失败 = 员工完全无法进入 | 建议加"刷身份证"兜底；或在告知书中明确该限制 |
| R12 | **不启用超时升级 + 不允许代审批** | 审批人不响应时访客只能被拒 | 客户书面确认；前台 SOP 明确"只能等待或不放行" |

### 11.2 前提假设

1. 设备固件版本 ≥ 2022-11（支持在线比对接口）
2. 设备可主动访问公网 HTTPS
3. 平台可自建 EMQX 并开放 1883/8883 端口
4. 客户接受"断网时未在本地的访客无法进入"
5. 客户接受"审批人未响应时访客无法进入"（或同意备用审批人机制）

## 14. 需求确认记录

> 本表记录需求评审中的确认结论，作为 v1.0 → v1.1 的变更依据与验收溯源。

| # | 确认事项 | 结论 | 影响 |
|---|---|---|---|
| C1 | 访客是否采集人脸 | **不采集**。访客仅刷身份证（1:1 人证）+ 白名单 | 无需访客底库，合规最干净 |
| C2 | 员工是否刷身份证 | **不刷**，仅刷脸（1:N） | 员工必须下发模板照 |
| C3 | 员工刷脸失败的替代方式 | **前台远程开门（人工核验）** | 断网时该路径失效（见 R11） |
| C4 | 员工信息与照片维护 | **PC 管理后台**统一维护 | 员工端无自助采集入口 |
| C5 | 员工照片审核 | **上传人即审核人**，保存即生效 | 无独立审核流程，需变更留痕 |
| C6 | 员工通行范围 | **全部门点**，不做分级授权 | person 不设门点维度 |
| C7 | 访客通行门点 | **仅公司大门一个门点**，预约不选门点 | 单门点模型，大幅简化下发 |
| C8 | 备用审批人超时升级 | **不启用**，只能等待或不放行 | 现场僵局风险（见 R12） |
| C9 | 前台代审批 | **不允许** | 同上 |
| C10 | 数据保留期限 | 抓拍/证件照 **30 天**；通行与审批记录 **12 个月** | 清理任务与存储规划 |
| C11 | 短信通道 | **不可用**，仅小程序 + PC | 待办角标为唯一可靠通知通道 |
| C12 | PC 审批实现 | uni-app 编译 H5；小程序扫码登录；登录态 8 小时 | 不依赖短信验证码 |
| C13 | 审批级数 | 可配 1 级或 2 级，不做 3 级 | 二级从候选池指定一人 |
| C14 | 代邀与审批的关系 | 代邀时一级审批**自动通过** | 邀请人 = 一级审批人 |
| C15 | 现场登记 | **也走完整审批**，无快速通道 | 依赖审批人响应速度 |
