## 1. 联调已证实的事实（决定架构的硬约束）

2026-11-16 在 YC-P208（SN `T77R781116ZS`，固件 `V1.11248.20260616-C978GH-DHCP`）上实测：

| 结论 | 证据 | 架构含义 |
|---|---|---|
| **平台能主动调设备 8091** | `/deviceLogin`、`/getDeviceParameter`、`/setDeviceParameter`、`/addDeviceWhiteList` 全部 `result=0` | 名单下发、参数配置、远程开门都可以**由平台推**，不需要等设备来拉 |
| **设备能主动推平台** | 心跳每 30 秒一次，含 `SN/ip/personCount/currentTime`；日志确认 `rspData={"message":"ok","result":0}` | 心跳与通行记录走"设备→平台"回调，平台需常驻 HTTP 接收端 |
| **设备出厂绑了厂商云** | 日志每 20 秒 `POST https://jdpw.jiudingjituan.cn/device/login`，`register_no=RV1109-...`，另有 `frpc loading...` | 云通道**不可依赖**（现场无外网），但双通道架构下可复用该协议 |
| **读卡器未就绪** | 全量 8292 行日志仅开机一条 `serialPortIdCardScan 串口打开成功 /dev/ttyS5`、`check uart connect device type:0`，刷卡无任何事件 | 身份证链路**暂不可验**，进度计划中列为外部依赖 |
| 在线比对是"等云"的 | `Comparison=1` 时指向厂商云，无外网则刷卡/刷脸静默失败 | 现场必须切 `Comparison=0`（离线比对）或指向自有平台 |

> **由此确定：不是"设备主动来拉名单"的云模型，而是"平台推 + 设备回调"的局域网模型。** 云模型作为备用通道保留，两者共用同一套业务服务。

> **开发要点（已实测）**
> 1. 该开关的「仅适用于 702K」说明解释了为什么 `intranetSetting=1` 下发后云登录仍在继续（日志 265 次）。**平台不要依赖这个参数切换内外网**，通道选择应由设备档案的 `channel` 字段决定。
> 2. 界面「人脸识别=禁用」与接口 `recogModeDB=1` 的取值**不一致**，实施时需以**接口回读值**为准，并在设备看板展示回读值（UI 可能是本地缓存）。此项列入开发验证点。
> 3. 参数下发的正确姿势：先 `getDeviceParameter` 取全量 → 只改目标字段 → 整体回写，避免把未展示的字段重置成默认值。

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│  接入层                                                       │
│  小程序/H5(访客·员工)   PC管理后台   Kiosk(门卫室电脑)         │
└───────────────┬──────────────────────────────────────────────┘
                │ HTTPS / JSON
┌───────────────▼──────────────────────────────────────────────┐
│  应用层  Spring Boot 单体（按模块分包，便于后续拆分）           │
│  visitor  employee  approval  credential  access  device      │
│  report   notify    admin    audit    job                     │
└───────────────┬──────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────┐
│  设备适配层（本次架构重点）                                    │
│  DeviceAdapter（接口）                                        │
│   ├─ LanHttpAdapter     → 调设备 8091（已联调）               │
│   └─ CloudMqttAdapter   → /device/login + MQTT（备用）        │
│  DeviceGateway：选择适配器、串行队列、重试、幂等、指标          │
└───────────────┬──────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────┐
│  基础设施  MySQL  Redis  对象存储(照片)  定时任务  日志/监控    │
└──────────────────────────────────────────────────────────────┘
```

### 2.1 双通道适配层（按你的选择）

对外只暴露一组**统一语义**的接口，内部按设备能力选通道：

| 统一方法 | 局域网 HTTP 实现 | 云 MQTT 实现 |
|---|---|---|
| `login()` | `POST /deviceLogin` | `POST /device/login` → token + mqinfo |
| `getCapability()` | `GET /getDeviceParameter` + `/getDeviceVersion` | MQTT `get_basic_settings` |
| `upsertVisitor(person)` | `POST /addDeviceWhiteList`（`passAlgo=true`） | `sync_card` |
| `upsertEmployee(person)` | `POST /addDeviceWhiteList`（`passAlgo=false` + `register_base64`） | `sync_person` |
| `removePerson(id)` | `POST /deleteDeviceWhiteList` | `delete_person` |
| `clearAll()` | `POST /deleteDeviceAllWhiteList` | `delete_all` |
| `listPersons()` | `POST /getAllDeviceIdWhiteList` + `/getDeviceWhiteListDetailByIdNum` | `get_person_all` / `get_person` |
| `openDoor()` | `POST /setDeviceRemoteOpen` | `open_door` |
| `setTime()` | `POST /setDeviceTime` | `sync_time` |
| `setParams(cfg)` | `POST /setDeviceParameter` | `set_basic_settings` |
| `showMessage(msg)` | `POST /setDeviceShowMessage` | 不支持（能力位标记） |
| 心跳来源 | 设备推 `heartBeatIp`（30s）+ 平台可调 `/heartBeat` | 设备登录即心跳（30s） |
| 记录来源 | 设备推 `platformIp`（须回 `{"message":"ok","result":0}`） | `POST /record/upload/online` |

**选型规则**（写进配置，不写死代码）：设备档案上带 `channel` 字段（`LAN` / `CLOUD`），以及 `capability` 位（是否支持身份证读头、二维码、在线比对、远程开门）。

> 好处：现场若是内网就用 LAN；若某天设备只能出公网（例如 4G 点位），改一个配置字段即可切 CLOUD，业务代码零改动。

### 2.2 技术栈（沿用已确认的 C-09/C-10）

| 层 | 选型 | 依据 |
|---|---|---|
| 后端 | Java 17 + Spring Boot 3.x + MyBatis-Plus | C-09（Java + MySQL） |
| 数据库 | MySQL 8 | C-09 |
| 缓存/队列 | Redis（去重、幂等、待办计数、轻量队列） | 心跳去重、指令串行 |
| 文件 | **MinIO（内网）**，S3 兼容 SDK；`StorageService` 接口隔离，切云 OSS/COS 只改配置 | 照片私有存储 + 短时预签名 URL（BR-D-002 等） |
| 前端 | uni-app（小程序 + H5 一套代码） | C-10 |
| PC 后台 | Vue 3 + Element Plus | 与 uni-app 同生态 |
| 设备对接 | `HttpClient`（LAN）/ EMQX + Eclipse Paho（CLOUD） | 06 / 07 协议 |
| 部署 | 单机 Docker Compose（MySQL/Redis/应用/Nginx）+ MinIO（同机或内网另一台） | 客户规模 100 人、单门点，单体最省 |

### 3.2 建议开发顺序（按"能不能演示"排）

```
阶段一（骨架可跑，能对接设备）
  M1 基础框架 → M3 设备中心（先 LAN 通道）→ 设备看板能看到心跳

阶段二（业务主链打通，可内部演示）
  M2 员工 → M4 访客预约 → M5 审批 → M6 授权下发 → M8 记录接收
  验收标志：手机上提交预约 → 审批通过 → 设备名单里出现该人 → 刷证产生记录

阶段三（访客自助与凭证）
  M7 二维码 → M10 访客端/员工端 → M11 保安工作台
  验收标志：未带身份证的人扫动态码开门（需设备支持在线二维码）

阶段四（管理端与报表）
  M9 管理后台 → M12 定时任务

阶段五（双通道与交付）
  M3 增补 CloudMqttAdapter → M13 部署上线
```

> **为什么设备中心放最前**：它是外部依赖最多、最容易返工的部分。先把 LAN 通道和心跳跑通（本次已基本验证），后面业务模块才有可靠的"下发"落点。

## 5. 接口契约

### 5.1 分组与鉴权

| 分组 | 前缀 | 调用方 | 鉴权 |
|---|---|---|---|
| 访客/员工端 | `/api/app/**` | 小程序、H5 | 微信登录态 / 手机号验证码 |
| 管理后台 | `/api/admin/**` | PC 后台 | JWT + RBAC |
| 保安工作台 | `/api/guard/**` | Kiosk | JWT（保安角色） |
| **设备回调** | `/api/device/callback/**` | 门禁终端 | 设备 SN + 平台预共享密钥签名 + IP 白名单 |
| 对内设备指令 | Service 层 | 应用内部 | — |

### 5.2 设备回调接口（**设备调我们**，需先于业务开发）

| 方法 | 路径 | 用途 | 关键约束 |
|---|---|---|---|
| POST | `/api/device/callback/heartbeat` | 心跳（30s） | **必须回 `{"message":"ok","result":0}`**；按 SN 更新在线状态；`personCount` 记录容量水位 |
| POST | `/api/device/callback/record` | 通行记录 | 必须回 `{"message":"ok","result":0}`，否则设备**一直重推**；用 `id` 做幂等；`face_base64` 异步转存 |
| POST | `/api/device/callback/compare/online` | 在线比对（动态二维码/人证） | 同步返回 `{"status":0,"msg":"","audio":""}`；P99 < 300ms；**不得访问远程服务** |
| POST | `/api/device/callback/qrcode` | 二维码在线识别（部分固件） | 同上 |
| POST | `/api/device/callback/notify` | 指令执行回执（云通道用） | 更新 `device_cmd` 状态 |

**记录回调返回体（严格照协议）**：

```json
{"message":"ok","result":0}
```

**在线比对返回体**：

```json
{"status":0,"msg":"识别成功","audio":"识别成功"}
```

### 5.4 统一响应与错误码

```json
{"code":0,"message":"ok","data":{}}
```

| 码段 | 含义 |
|---|---|
| 0 | 成功 |
| 1xxx | 参数/校验错误 |
| 2xxx | 鉴权/权限 |
| 3xxx | 业务规则冲突（如时段冲突、黑名单命中） |
| 4xxx | 设备通道错误（超时、离线、设备返回 result≠0） |
| 5xxx | 系统错误 |

### 5.5 设备通道的错误映射（双通道统一）

| 场景 | LAN HTTP 表现 | 云 MQTT 表现 | 统一错误码 |
|---|---|---|---|
| 设备离线 | 连接超时 | 无 ack / MQTT 断连 | 4001 |
| 密码错误 | `result=2` | `code≠0` | 4002 |
| 参数错误 | `result=1` | `success=false` | 4003 |
| 队列积压 | 本地串行队列长度超阈值 | MQTT QoS 积压 | 4004 |

## 6. 关键技术决策（含理由与代价）

| # | 决策 | 理由 | 代价/风险 |
|---|---|---|---|
| D-1 | 设备对接做**适配层双通道** | 现场是内网（LAN 已通），但可能出现仅有公网的点位；且厂商云协议可复用 | 多写一套适配器，测试面翻倍 |
| D-2 | 名单下发采用**平台推**为主（LAN），对账定时兜底 | 实测平台可直接调 8091，比"等设备来拉"实时性高 | 需要设备常在线；离线期间变更需排队 |
| D-3 | 在线比对接口**独立线程池 + 本地缓存**，不查远程 | 协议要求 P99<300ms，门口不能等人 | 缓存一致性需靠事件驱动刷新 |
| D-4 | 记录回调**先落库再返回 ok**（照片异步） | 设备不收到 ok 会无限重推 | 落库失败要快速失败，不能假装成功 |
| D-5 | 动态二维码**平台实时校验**，不下发设备 | 60 秒动态码无法预下发 | 断网时二维码不可用（BR-V-022 已确认接受） |
| D-6 | 访客**不采集人脸**，员工**仅刷脸** | 客户已确认（C-14/C-18），合规最简 | 员工刷脸失败依赖人工开门 |
| D-7 | 单门点模型（入口/出口各一台，共用一个门点） | C-19 | 后续扩门点需改授权模型（已按"人+门点"设计，预留） |
| D-8 | 身份证通行**标记为外部依赖** | 厂商称需外网，未验证 | 若最终不可用，访客主通道退化为动态二维码 |
