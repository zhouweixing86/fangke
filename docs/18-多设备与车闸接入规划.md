# 18 多设备与车闸接入规划

> 版本 v1.0 ｜ 2026-11-24
> 读者：项目经理、实施、厂商对接、开发
> 结论先行：**人行闸的进门相机已调试完毕**；出口相机（同品牌）按"同一门点 + 方向=出口"再挂一台即可，平台侧无需改代码；
> **车闸相机（两台、异品牌）已完成架构与接口预留**，等厂商协议文档到位后按 §4 接入。
>
> **2026-11-25 更新（C-86）**：出口车闸走的是**云车场开放平台**（不是相机本地 HTTP），
> 车牌下发通过 `visitor_sync` 接口按车牌增/改/删，已实现并做了 dry-run 验证。
> 具体接口、签名与待车场提供的资料见 [19-车闸开放接口-云车场V1.1](./19-车闸开放接口-云车场V1.1.md)；本文的"相机本地下发"方案作为备选保留。

## 2. 出口相机（同品牌 YC-P208）

### 2.1 平台侧要做的事（3 步，全部在界面完成）

1. 设备上电联网，按 [17 §3](./17-设备接入配置手册.md) 配「第三方设备管理平台-HTTP」，地址与 `thirdHttpkey` 跟进门相机一致
2. 设备管理 → **人行终端** → 看到自动登记的新设备（在「待分配」）
3. 档案里设置：
   - **所属门点 = 和进门相机同一个门点**（这是关键，名单按门点下发）
   - **方向 = 出口**
   - 设备名称如「A 栋东门·出口」

保存后最多等一个心跳周期（5 秒），设备开始拉名单。

### 2.2 平台已经支持，不需要改代码

| 能力 | 为什么不用改 |
|---|---|
| 同一门点多台设备 | 下发按 `gate_id` 找设备集合，门点下有几台就发几台（`DispatchService` / `EmployeeDispatchService`） |
| 方向 | `device.direction` 会在 `syncDeviceParameter` 里作为 `inout` 下发给设备；出口机识别后上报 `inout=0` |
| 出门记录 | `inout=0` → 记为「出」，访客自动**签离**（`VisitRecordService` 只看方向，不推断） |
| 出口机未上报 `inout` | 平台回退用**设备档案的方向**，不会把出门记成进门（2026-11-24 修复） |
| 开门 | 远程开门按**设备 id**，想开哪个门就点哪台；闸机常开/校时同理 |
| 二维码 | 出口一般不需要扫码出；若需要，核验按扫码那台设备的门点判定 |

### 2.3 验收清单（出口相机装好后逐条打勾）

1. 设备管理里能看到两台设备，门点相同、方向一进一出
2. 设备后台参数 `inout=0`（出口）
3. 下发名单后两台设备 `curCount` 都 +1
4. 刷证进门 → 通行记录「进」；刷证出门 → 通行记录「出」，访客预约状态变「已签离」
5. 设备管理点「开门」只开对应方向那台
6. 停用/恢复员工，两台设备人数同步增减

### 2.4 注意事项

- **不要**给出口机单独配一套人事名单，两台都靠平台按门点下发，避免两边不一致
- 出口机如果不装读卡器/摄像头，能力矩阵里会缺项，届时在设备档案 `capability` 里按台关闭即可
- 两台设备的 SN 必须不同（固件按 SN 区分设备，SN 相同会互相覆盖）
- 设备列表的「在线」按**心跳新鲜度**判断（3 个心跳周期、最少 60 秒）：断电后会显示离线，不会一直挂在"在线"

## 3. 车闸相机（两台，异品牌）

### 3.1 与 YC-P208 的本质区别

| 维度 | 人行终端 YC-P208 | 车闸相机（异品牌） |
|---|---|---|
| 名单对象 | 人员（姓名/证件/照片） | **车牌** |
| 名单来源 | 员工 + 访客授权 | 员工 `plate_no` + 访客预约 `plate_no` |
| 平台角色 | 设备来拉名单，平台下发 | 相机推车牌，**平台判定后回 `openGate`** |
| 是否要本地名单 | 要（断网也能开） | 视厂商能力：能接指令的不需要；全自治的才需要同步 |
| 通道 | `PULL` | `VEHICLE`（本次新增，用于单独管理） |

### 3.2 车牌数据从哪来（不新建"车牌授权表"）

| 来源 | 字段 | 有效期 | 门点 |
|---|---|---|---|
| 员工白名单 | `employee.plate_no`（员工档案里填） | 员工有效期（`valid_from`~`valid_to`） | 全部启用门点 |
| 访客预约 | `appointment.plate_no`（访客预约表单里填） | 预约当天 `start_time`~`end_time` | **审批批准的门点** |

> 所以"白名单"和"访客"填车牌这件事**已经在做了**（C-68），平台侧清单随时可查，
> 缺的只是"把清单投到异品牌相机本地"这一步。

### 3.3 单独管理

车闸相机在设备管理里**单独一个页签**（`channel=VEHICLE`），与人行终端互不干扰：

- 车闸相机不会收到人员名单：平台下发人员/黑名单时会**直接跳过** `VEHICLE` 设备，不会产生"部分失败"批次；
  即使手工对车闸相机触发，也会被明确拒绝（避免把人脸/证件推给车闸）
- 车闸相机的 `openDoor`/屏幕提示/校时等人行能力一律"不支持"（车闸由相机自己开闸）
- 首次收到车牌事件自动登记到「待分配」门点，现场按 §4.3 分配

### 3.4 判定规则（已实现，`VehicleAccessService`）

| 车牌属于 | 放行条件 | 拒绝示例 |
|---|---|---|
| 员工 | `employee.plate_no` 匹配 + 在岗 + 在有效期内 | 员工通行证已过期 |
| 访客 | 当天预约 `plate_no` + 状态可通行/已签到 + **批准门点包含当前门** | 该车牌今日已授权，但不包含当前门点 |
| 其它 | 拒绝 | 未登记车辆（车牌未绑定员工，也没有今日访客预约） |

门点无法确定时**一律拒绝**（防止跨门误放），所以相机必须能给出 `deviceno` 或 `gateId` 之一。

## 4. 车闸接入步骤（拿到厂商文档后照着做）

### 4.1 厂商必须提供的 5 件事

| # | 要什么 | 用途 |
|---|---|---|
| 1 | 车牌事件推送接口（URL、报文、鉴权方式） | 相机 → 平台，现有 `/openapi/v1/vehicleEvent` 已兼容常见字段 |
| 2 | 返回什么字段才开闸（`openGate`? `code`? 文本?） | 决定相机是"平台判定"还是"本地判定" |
| 3 | 车牌名单下发接口（**如果支持**） | 下发到相机本地，断网也能放行 |
| 4 | 车牌名单容量与生效延迟 | 清单超过容量要提前告知 |
| 5 | 开闸方式（干接点/继电器/485/网络指令） | 现场接线与是否需要平台直连道闸控制器 |

### 4.2 平台侧已预留的接口

| 方法 | 路径 | 状态 | 说明 |
|---|---|---|---|
| POST | `/openapi/v1/vehicleEvent` | ✅ 已实现 | 相机推车牌，平台判定并回 `openGate`；字段别名兼容、幂等、抓拍入库 |
| GET | `/api/admin/vehicle/device?gateId=` | ✅ 已实现 | 车闸相机列表（单独管理） |
| GET | `/api/admin/vehicle/plate?gateId=` | ✅ 已实现 | 车牌清单快照（员工 + 当天访客，含来源/有效期） |
| POST | `/api/admin/vehicle/plate/sync?gateId=` | ✅ 已实现（**投递待厂商**） | 把清单推给车闸相机；协议未接入时返回 `PENDING_VENDOR` |
| — | `DeviceAdapter.pushPlates` / `removePlate` | ✅ 接口已留 | 厂商适配器只需实现这两个方法 |
| — | `Device.Channel.VEHICLE` | ✅ 已实现 | 车闸相机通道，与 `PULL` 分开选适配器 |

**厂商协议到位后只改一个类**：`VehicleCameraAdapter` 里填 `pushPlates`/`removePlate` 的 HTTP 报文，
再把 `capabilities()` 加上 `PLATE_UPSERT` / `PLATE_REMOVE`，其余业务代码零改动。

#### 已用模拟报文实测（2026-11-24，暂未上真机）

| 验证点 | 结果 |
|---|---|
| 相机推车牌 `POST /openapi/v1/vehicleEvent` | `openGate=1`，匹配员工，落车辆通行记录 |
| 首次上报自动登记 | 设备管理「车闸相机」出现新设备（`channel=VEHICLE`，待分配，在线） |
| 车牌清单 `GET /api/admin/vehicle/plate` | `{employee:1, visitor:0, total:1}`，来源/有效期正确 |
| 名单下发 `POST /api/admin/vehicle/plate/sync` | `PENDING_VENDOR`，提示"平台已备好 1 条车牌，等车牌下发接口文档" |
| 人员名单隔离 | 同门点下人行终端照常下发（1/1 成功），车闸相机被跳过 |
| 设备列表按通道过滤 | `/api/admin/device?channel=VEHICLE` 只返回车闸相机 |

> 测试数据已清理（临时设备/车牌/车辆记录），现场看到的仍是真实的人行终端一台。

### 4.3 现场接入顺序

1. 相机接网，配置"平台地址"（不同厂商叫法不同：第三方平台/服务器地址/HTTP 推送）
2. 让相机推一条测试车牌事件，平台侧确认：设备管理 → 车闸相机 页出现新设备（待分配）
3. 档案里分配**真实门点** + 方向（入口/出口）
4. 员工档案 / 访客预约里填车牌 → 设备管理 → 车闸相机 → **车牌名单** 页核对清单
5. 厂商协议接入后点「下发到车闸相机」；在此之前清单只作核对用
6. 实车测试：白名单车靠近 → 闸开；未登记车 → 拒绝并记录

### 4.4 验收清单

1. 车闸相机在「车闸相机」页签可见，门点/方向正确，在线
2. 员工填了车牌，清单里出现该车牌，来源=员工
3. 访客预约填了车牌并审批通过，清单里出现该车牌，来源=访客，门点=批准门点
4. 审批未通过/门点不符的车牌**不出现**在清单里
5. 实车进场：白名单车放行，平台有车辆通行记录
6. 实车出场：方向=出，记录正常
7. 未登记车：拒绝 + 原因可查（车辆通行记录页）
8. 断网策略按厂商能力确认（能本地判定的，名单要提前下发）

## 5. 待厂商确认的问题清单（发给对接人）

1. 车牌事件推送是否支持 HTTP POST？URL、报文示例、是否需要签名
2. 推送里能否带**设备唯一号**（SN/MAC）？能否带**门点/相机编号**？
3. 平台返回值怎么让相机开闸？字段名与取值（`openGate=1`?）
4. 是否支持平台下发车牌白名单？接口、容量、生效延迟
5. 名单是"覆盖"还是"增量"？删除车牌用哪个接口？
6. 相机本地名单满/断网时的行为？
7. 开闸是相机自己控制继电器，还是要平台给道闸控制器发指令？
8. 心跳/在线状态怎么上报？平台如何判断相机离线？
9. 抓拍图能否一起推（base64 或 URL）？
10. 是否支持时间同步、远程重启？
