# 人员通行方式与流程（员工 / 访客）

> 版本 v1.0 ｜ 2026-11-19
> 回答两个问题：**员工怎么进厂区**、**访客审批通过后怎么在各个门通行**。
> 本文只写**代码里已经实现的行为**，未实现的会明确标「缺口」。

---

## 1. 一句话结论

| 人员 | 通行方式 | 状态 |
|---|---|---|
| **员工** | 刷**人脸** / 刷**身份证** | ✅ 已实现（入职即下发到全部启用门点） |
| **员工离职/停用** | 自动撤销授权 + 从设备删除 | ✅ 已实现 |
| **访客** | **只能刷身份证**（+ 出示动态二维码） | ✅ 已实现（双审通过后下发） |
| **访客刷脸** | ❌ **不允许**（2026-11-21 客户确认，已移除采集入口与下发照片） | 已按需求关闭 |
| 兜底 | 保安人工开门 | ✅ 已实现 |

> **访客禁止刷脸的口径**（客户 2026-11-21 确认）：访客到闸机必须刷身份证，
> 因此平台**绝不下发访客照片**（`passAlgo=true`）、访客端也**没有**人脸采集入口。
> 一旦下发照片，设备就会用照片做刷脸比对，等于绕过"必须刷证"的要求。
> 由此带来两条连带规则：**访客本人身份证必填**；同行人只登记**姓名 + 手机号**，跟随本人一次放行（不再单独刷证，C-111）。

## 2. 员工通行（已实现）

### 2.1 下发链路

```
新增员工 / 编辑 / 换照片 / Excel 导入
   → 给**每个启用门点**建一条长期授权
        access_grant(subject_type=1 / 员工)
        valid_from = 入职日（没填=今天）
        valid_to   = 离职日（没填=9999-12-31）
   → 推到这些门点下的设备（含人脸照片 base64）
   → 设备名单里 usertype=white、groupSuffix=员工

停用员工
   → 撤销全部授权（status=4）
   → 从各门点设备删除该人
```

- **入职即生效**：保存员工后立刻下发，不用等定时任务。
- **全部门点**：厂区 4 个门都会收到，员工哪个门都能刷。
- **新增门点后**：点一次「同步名单」（或等每天对账）把老员工补到新门点。
- **手动补偿**：员工管理页有「同步名单」（全量）和每行「下发」（单人）。

### 2.2 到了门口怎么开

| 方式 | 说明 |
|---|---|
| **刷脸** | 设备本地比对名单里的人脸特征；员工档案必须**已上传照片**（未上传则 `passAlgo=true`，只能刷证） |
| **刷身份证** | 名单里 `idno` = 员工身份证号；员工未填身份证时用品编号兜底 |

> 实测（DEMO-EAST-01）：`getDevicWhiteInfo` 返回 `usertype=white`、`groupSuffix=员工`、`passAlgo=false`、`picData1` 有照片。

## 3. 访客通行（已实现）

### 3.1 授权怎么产生

```
访客提交预约（微信小程序，选门点 / 全部门点）
   → 待审核（PENDING_L1）：任务指派给**管理端角色 GUARD**（保安/管理员，谁值班谁审）
   → 管理端审核通过 → 下发门禁授权
        access_grant：**每个批准门点一行**
        valid_from = 预约当天 00:00:00
        valid_to   = 预约当天 23:59:59   （按自然日整段，C-60）
   → 设备收到该人员（名单里 idno = 身份证号）
```

> **2026-11-21 起为单级审批（C-70）**：员工不再登录审批，被访人只作为"拜访对象"记录。
> 审核入口 = 管理端 Web「保安工作台 → 待我审核」或管理端 H5 同一页面。
>
> **2026-11-24 起支持多级审批 + 抄送（C-72）**：管理端「审批配置」可增删节点、配处理角色与
> 单签/会签/或签；节点串行，**最后一个节点通过才下发**；抄送只通知不阻断（提交时 / 节点办结后）。

- **有效期**：只在这一天有效，第二天自动失效（过期 7 天后由清理任务从设备移除）。
- **门点范围**：只对**批准的门点**有效。去别的门刷，平台判定 `GATE_MISMATCH`（"门点不符"）拒绝。
- **申请"全部门点"**：审批通过时快照成当时启用的门点，事后新增的门不会自动开放。

### 3.2 到了门口怎么开

| 方式 | 走什么链路 | 说明 |
|---|---|---|
| **刷身份证** | 设备本地比对名单（`idno` = 身份证号）→ 开门 → 推通行记录 | **唯一的人脸/证件方式**，必填证件号才有名单 |
| **动态二维码** | 访客手机出示 → 设备扫码 → 推 `qrCodePush` 给平台 → 平台判定后回 `openGate` | 码 60 秒一轮、**期内可重复使用**（BR-V-020） |
| **刷脸** | ❌ 禁用 | 平台不下发访客照片（`passAlgo=true`），设备不会用照片比对；访客端已无采集入口 |
| **保安人工放行** | 保安在门卫工作台点「开门」或扫码核验 | 异常兜底；必填原因，落 `access_event(source=3)` |

### 3.3 访客照片采集（已废弃）

2026-11-21 客户确认：**访客只能刷身份证，不允许刷脸**。因此：

- 后端 `POST /api/app/me/face` 已删除，`VisitorFaceService` 已移除
- 访客端「我的」页的人脸采集卡片已移除，改为提示"到闸机时请刷身份证进门"
- 下发链路 `OpenApiDeviceService.visitorPhoto()` 固定返回 `null` → 设备收到 `passAlgo=true`，
  即使数据库里残留历史照片也不会推到设备
- 连带规则：访客本人身份证**必填**；同行人只留姓名 + 手机号，跟着本人一起进（C-111）

> 员工不受影响：员工仍走人脸 + 身份证。`/api/admin/employee/{id}/face` 保持不变。

### 3.4 进场后的动作

```
设备推通行记录 uploadDetectRecord
  → access_event（通行留痕：门点、时间、识别方式、抓拍）
  → visit_record（首次进门自动"签到"，离场刷证/保安签离）
```

- 识别方式落库为 `identify_type`：0 人脸 / 2 人证 / 3 IC 卡 / 5 二维码 / 6 密码 / 9 人工开门。
- 同行人：统一 `mateMode=0`（随行一次放行），只登记姓名 + 手机号，不单独下发、不单独出通行记录（C-111）

## 4. 对照表

### 4.1 识别方式支持情况

| 识别方式 | 员工 | 访客 | 备注 |
|---|---|---|---|
| 人脸 | ✅ 需上传照片 | ✅ 需自助采集 | 未采集时设备按 `passAlgo=true` 跳过人脸 |
| 身份证 | ✅ | ✅ | 员工未填身份证时用品编号兜底 |
| IC 卡 | — | — | 本期不做 |
| 动态二维码 | — | ✅ | 平台签发、平台判定 |
| 人工开门 | ✅ | ✅ | 保安工作台，必填原因 |

### 4.2 谁能放人进厂区

| 环节 | 谁 | 作用 |
|---|---|---|
| 预约 | 访客本人（微信小程序） | 提交来意、被访人、申请门点，可填随行人员（姓名 + 手机号）；二维码默认开通，无需勾选 |
| 审核 | **管理端登录人**（节点配置的角色） | 多级（可配）：每个节点审核自己的环节；末级通过才下发。可增减门点、可拒绝并填原因（二维码不再由审批决定，C-111） |
| 抄送 | 配置的角色（管理端账号） | 提交时 / 节点办结后站内通知，只告知不阻断 |
| 现场通行 | 设备 | 刷证 / 扫码比对，自动放行并留痕 |

> **2026-11-21 起为单级审批（C-70）**：员工不参与审批，被访人只是"拜访对象"记录。
> **2026-11-24 起支持多级 + 抄送（C-72）**：节点、处理角色、单签/会签/或签、抄送对象都在
> 管理端「审批配置」里维护；没有模板时退回单级角色审批。
> 员工本人属"长期授权"，走的是入职下发链路，不经过访客审批。

## 5. 进出双向与车辆（C-67）

### 5.1 一个门 = 4 台设备

```
门点 A
 ├── 入口行人闸机（direction=1）  刷脸/刷证 进
 ├── 出口行人闸机（direction=0）  刷脸/刷证 出
 ├── 入口车辆闸机（direction=1）  二期：车牌识别
 └── 出口车辆闸机（direction=0）  二期：车牌识别
```

- 授权按**门点**下发，门点下**所有设备**（不分方向）都收到同一个人 → 进出都能刷
- 设备档案里用 `direction` 标进出；通行记录按 `direction` 分别记「进场/离场」
- 访客在出口刷到 = 自动**签离**；员工在出口刷到 = 离场记录
- **不需要改代码**，现场把每台闸机的 `direction` 配对即可

### 5.2 车辆（一期已实现，C-68）

> 现场核实：**一个门 = 1 台车闸（双向）+ 1 台行闸（双向）**。

```
车牌相机/车闸一体机
   → POST /openapi/v1/vehicleEvent（车牌、门点、方向、时间、抓拍）
   → 平台实时判定：
        员工车牌 → employee.plate_no 匹配 + 在岗 + 有效期 → 全部启用门点放行
        访客车牌 → appointment.plate_no + 状态 35/40 + 当天 + **批准门点** → 放行
        其它     → 拒绝（未登记车辆）
   → 返回 openGate（能接指令的车闸据此开闸）
   → 落 vehicle_event（车牌/门点/方向/匹配人/放行结果/抓拍）
   → 管理端「车辆记录」可查
```

| 项 | 状态 |
|---|---|
| 员工车牌 | ✅ 员工档案 `plate_no`，长期有效 |
| 访客车牌 | ✅ 预约填车牌（`appointment.plate_no`），审批通过后按当天 + 批准门点生效 |
| 车辆通行记录 | ✅ 管理端「车辆记录」页 |
| 车闸开闸 | ⏳ 取决于相机是否支持"接收开闸指令"（厂商待确认）；不支持则相机本地判定、平台只留记录 |
| 司机核验 | ❌ 只认车牌，不核验车内人员 |

> 判定**不另建车牌授权表**：直接复用员工档案与访客预约（同一套门点、同一天有效期）。

## 6. 黑名单（2026-11-21 实现下发）

拉黑有两个作用面，**身份证类型**两个都生效，**手机号类型**只有第一个：

| 作用面 | 生效方式 | 延迟 |
|---|---|---|
| 平台侧拦截预约 | 创建预约时校验 `target_hmac`，命中直接返回 `3003 命中黑名单` | 立即 |
| **设备侧拒绝通行** | 下发到设备本地黑名单（`usertype=black`），刷证时设备自己拒绝 | ≤ 一个心跳周期（现 5 秒） |

联动动作：

| 操作 | 平台侧 | 设备侧 |
|---|---|---|
| 新增黑名单（已生效） | 落库（密文 + HMAC + 脱敏） | 入队 `ADD_PERSON`，`usertype=black` |
| 立即生效 | 撤回待审批预约、撤销已下发授权、作废通行码 | 同上 + 从白名单删人 |
| 失效 / 恢复可预约 | 状态置 0，不再拦截预约 | 入队 `DEL_PERSON`，从设备黑名单删除 |
| 恢复生效 | 状态置 1 | 重新入队 `ADD_PERSON` |

关键实现点：

- 黑名单详情按身份证号判定（`isBlacklisted(TARGET_ID_CARD, hmac, now)`），命中时**优先按黑名单返回**，
  即使这个人同时有生效授权也不会被当成白名单放行
- `getAllDeviceWhiteList`（设备开机拉全量索引）里**包含黑名单 idno**，
  否则设备会把本地黑名单当成"平台已删除"清掉——设备每天 03:00 自动重启，这条必须成立
- 指令 payload 同时带 `personNo` 与 `idno`（都是证件号）：`personNo` 用于去重与回执匹配，
  `idno` 是设备侧主键
- 解密失败的黑名单不会中断下发，只记 warn 并跳过

实测（真机 192.168.0.104）：拉黑前设备 `curCount=0` → 拉黑后 `1`（`ADD_PERSON` 回执 status=2）→
重新下发员工后 `2` → 黑名单失效后 `1`（`DEL_PERSON` 回执 status=2）。

## 7. 二维码开门（2026-11-27 改为默认开通）

访客刷身份证是主通道，二维码是**并行的默认通道**：所有预约都自带二维码，不需要访客申请、也不需要审批人单独同意（C-111）。

### 7.1 取码 → 进闸

```
预约审批通过（status = 30/35）
    → 访客「我的预约」列表点「出示通行码」（或直接进详情，进详情即自动出码）
    → 取码 POST /api/app/appointment/{no}/qr（60 秒有效，过期自动换新）
    → 闸机扫码 → 设备推 /openapi/v1/qrCodePush → 平台判定 → 回 openGate=1 → 开门
    → 通行记录记 1 条：扫码那台设备的 SN、设备方向、访客本人姓名（C-110）
```

### 7.2 关键规则

| 规则 | 说明 |
|---|---|
| 默认开通 | `appointment.qr_requested = qr_approved = 1`（创建时即写入），预约页不再有勾选框、审批页不再有开关 |
| 只受授权约束 | 取码仍校验「有生效授权 + 在授权时段 + 门点命中」（`GrantChecker`），未审批通过就取不到码 |
| 有效期 | 60 秒（`fangke.qr.ttl-seconds`），期内可重复核验；过期可刷新重取 |
| 保安/管理端不受限 | `CHANNEL_GUARD` / `CHANNEL_ADMIN` 是核验通道，不经过该门（现场应急仍可由保安出码） |
| 通行记录口径 | 只记**扫码进来的本人**一条；随行人员在预约详情/通行明细里展示，不单独成行 |

### 7.3 设备侧前置条件（重要）

闸机扫码需要设备两个开关都开：

| 设备参数 | 含义 | 平台能否远程改 |
|---|---|---|
| `videoScanQRcode` | **摄像头扫码**（默认 0 关闭） | ✅ 设备管理 → 远程管理 → 常用开关 |
| `QROpenEnable` | 二维码开门总开关（默认 1） | ✅ 同上 |

> 实测：远程把 `videoScanQRcode` 置 1 后，`/getDeviceParameter` 回读为 1，
> 设备用新码调 `qrCodePush` 返回 `{"openGate":1,"message":"核验通过，允许通行"}`。

远程开关只放行白名单三项（`videoScanQRcode` / `QROpenEnable` / `PasswordOpenEnable`），
其他参数改请在「本地管理」里操作——设备参数 100+ 项，全量开放迟早会被改到失联。
