## 1. 引言

### 1.1 业务背景

公司园区目前依靠人证核验终端对进出人员进行核查，但缺少配套的访客业务管理手段：

- 访客来访前无法提前登记，到访后只能在门卫处手工记录，信息不完整
- 员工无法提前知晓访客来访，也无法为访客提前办理进出手续
- 谁在什么时间进来、由谁批准、是否离开，事后无法追溯
- 通道授权依赖人工临时处理，访客在门口等待时间长
- 离职人员和过期来访人员仍可能继续通行

### 1.2 业务目标

1. **访客提前登记**：访客可在手机上完成预约，到访时直接刷身份证进入。
2. **审批可追溯**：每张预约单都有明确的审批人和审批意见，环节清晰。
3. **员工可为访客背书**：员工可主动邀请访客，减少访客等待。
4. **员工刷脸通行**：员工无需携带证件，刷脸即可进出。
5. **网络中断不影响通行**：断网期间，已获授权的人员仍可正常进出。
6. **全程留痕**：预约、审批、核验、进出均有记录，可查询、可追溯、可导出。

### 1.3 业务范围

**本期包含**

| 序号 | 业务内容 |

### 1.4 业务前提

本方案的业务设计基于以下前提，需在项目启动前确认：

1. 访客统一从**公司大门**进出，大门**入口与出口各设一台设备**，共用一个门点；预约时不区分入口/出口。
2. 员工可在**公司内全部门点**通行。
3. 员工以**刷脸**为唯一日常通行方式，不携带证件；刷脸失败时由**保安人工核实后开门**。
4. 访客**不采集人脸**；默认凭身份证完成人证核验，**未携带身份证时使用手机动态二维码**（60 秒有效、可重复通过）作为补充通行方式。
5. 设备具备断网离线运行能力，已获授权人员在断网时仍可通行。
6. 门禁为磁吸门，识别通过后自动释放，断电时门自动释放（消防要求）。
7. **本单位不设前台接待岗，现场接待由保安承担**：保安岗 24 小时值班，门卫室配有电脑与网络，可访问管理后台。
8. **现场登记 100% 由访客自助完成**：大门口张贴登记二维码，访客用手机扫码自行填表提交。
9. **保安不读卡、不代录、不做任何业务录入**；其职责仅为：查看（在访与待处理情况）、引导访客完成自助操作、以及在凭证不可用时远程开门。

## 2. 业务角色与职责

### 2.1 角色说明

| 角色 | 职责 | 使用入口 |
|---|---|---|
| **访客** | 提交预约、查看到访资格、出示凭证、按时到访与离开 | 手机（微信小程序 / 网页） |
| **员工（被访人）** | 审批来访申请、邀请访客、查看自己的访客 | 手机、电脑网页 |
| **二级审批人** | 对已通过一级审批的申请做二次审批 | 手机、电脑网页 |
| **保安** | 门卫岗。现场登记、跟踪审批进度、催办、人工开门、办理签离 | 管理后台 · 保安工作台 |
| **访客管理员** | 维护员工与人脸照片、黑名单、查询记录、出报表 | 电脑网页 |
| **系统管理员** | 账号与权限、审批配置、数据保留策略、审计 | 电脑网页 |

### 2.2 职责边界（重要）

| 事项 | 谁可以做 | 谁不可以做 |
|---|---|---|
| 批准访客进入 | 一级审批人、二级审批人、代邀员工（一级自动通过） | **保安无权批准** |
| 代替审批人做决定 | 无人可以 | 任何人 |
| 撤销已通过预约 | 管理员 | 保安 |
| 现场录入访客信息 | 保安 | 访客本人（需自行预约） |
| 人工开门 | 保安 | — |
| 维护员工人脸照片 | 管理员 | 员工本人、保安 |

> **明确规则**：系统**不提供**"保安代审批"和"超时自动放行"功能。审批人未处理时，访客只能等待或不被放行。此规则需客户书面确认。

## 3. 业务对象与生命周期

### 3.1 预约单

预约单是系统的核心业务单据，一张预约单对应"一位主访客 + 若干同行人"的一次来访。

```
草稿
  │ 提交
  ▼
待一级审批 ──驳回──▶ 已驳回（终止）
  │ 通过（若配置二级）
  ▼
待二级审批 ──驳回──▶ 已驳回（终止）
  │ 通过
  ▼
已通过 ──▶ 授权下发中 ──▶ 可通行
                            │ 首次通行
                            ▼
                          已签到
                            │ 签离
                            ▼
                          已签离

任一阶段可发生：
  申请人撤回 ──▶ 已撤回
  时段结束未到访 ──▶ 已过期
  管理员撤销 ──▶ 已撤销（若已授权，同步取消授权）
```

| 状态 | 业务含义 | 访客可见 | 可否通行 |
|---|---|---|---|
| 草稿 | 已填写未提交 | 可见 | 否 |
| 待一级审批 | 等待被访人处理 | 可见 | 否 |
| 待二级审批 | 等待二级审批人处理 | 可见 | 否 |
| 已驳回 | 被拒绝，含拒绝原因 | 可见 | 否 |
| 已通过 | 终审通过，正在授权 | 可见 | 否（授权未完成） |
| 可通行 | 授权已完成 | 可见（显示二维码） | **是** |
| 已签到 | 已到访未离开 | 可见 | 是（时段内） |
| 已签离 | 已完成本次来访 | 可见 | 否 |
| 已过期 | 时段结束未到访或未签离超时 | 可见 | 否 |
| 已撤回 | 申请人主动取消 | 可见 | 否 |
| 已撤销 | 管理员事后取消 | 可见 | 否 |

### 3.2 审批任务

| 状态 | 含义 |
|---|---|
| 待处理 | 已指派给审批人，尚未处理 |
| 已通过 | 审批人同意 |
| 已驳回 | 审批人拒绝，需填写原因 |
| 已跳过 | 因审批人与上一级为同一人，自动跳过 |
| 已转办 | 审批人将任务转给他人 |
| 已失效 | 审批人离职或预约单已结束 |

### 3.3 员工

```
在职 ──▶ 停用/离职 ──▶ 已删除（设备名单同步移除）
  │
  └── 有效期到期 ──▶ 待复核 ──▶ 续期 or 停用
```

| 状态 | 业务含义 | 可否通行 |
|---|---|---|
| 在职 | 可刷脸通行 | 是 |
| 待复核 | 有效期即将到期，需管理员确认 | 是（到期前） |
| 停用 | 已离职或暂停权限 | 否 |
| 已删除 | 从系统与设备中移除 | 否 |

### 3.4 访客

访客本身不设状态，其通行资格完全由"预约单 + 凭证"决定。

| 情况 | 处理 |
|---|---|
| 首次来访 | 建立访客档案 |
| 再次来访 | 按身份证号识别为同一访客，复用档案 |
| 有未完成的预约 | 提示"您已有一张进行中的预约" |
| 在黑名单中 | 提交时被拒绝 |

### 4.3 代邀规则（BR-I）

| 编号 | 规则 | 校验时点 | 违反时行为 | 优先级 |

## 5. 业务流程

### 5.1 场景一：访客自行预约（一级审批）

**参与方**：访客、被访人

| 步骤 | 操作人 | 动作 | 系统响应 |
|---|---|---|---|
| 1 | 访客 | 打开手机应用，微信授权登录 | 识别身份 |
| 2 | 访客 | 阅读并同意个人信息处理告知 | 记录同意时间 |
| 3 | 访客 | 填写姓名、手机、身份证号、被访人手机、访客类型、时段、（选填）车牌与事由；按需添加同行人 | 逐项校验（BR-P） |
| 4 | 访客 | 提交 | 生成预约单，状态"待一级审批" |
| 5 | 系统 | 按被访人手机号匹配员工 | 指派一级审批人，或使用默认审批人 |
| 6 | 系统 | 通知被访人 | 被访人手机端出现待办 |
| 7 | 被访人 | 查看来访信息，选择通过或驳回 | 通过 → 状态"已通过"；驳回 → "已驳回" |
| 8 | 系统 | 生成通行凭证，下发至大门设备 | 状态"授权下发中" → "可通行" |
| 9 | 系统 | 通知访客可通行 | 访客手机显示二维码 |
| 10 | 访客 | 到访，在大门刷身份证 | 设备完成人证核验，开门 |
| 11 | 系统 | 记录通行，自动签到 | 状态"已签到" |
| 12 | 访客 | 离开（再次刷证或保安签离） | 状态"已签离" |

### 5.2 场景二：访客自行预约（二级审批）

与场景一相同，区别在第 7 步之后：

| 步骤 | 操作人 | 动作 | 说明 |
|---|---|---|---|
| 7a | 一级审批人 | 通过，并**指定一名二级审批人** | 候选池仅 1 人时自动选中 |
| 7b | 二级审批人 | 查看来访信息与一级意见，通过或驳回 | 驳回则整单终止 |
| 7c | 系统 | 二级通过后生成凭证并下发 | — |

> 特殊情况：若二级审批人与一级为同一人，系统自动跳过二级（BR-A-007）。

### 5.3 场景三：员工代邀访客

**参与方**：员工、访客

```
员工在手机端选择「邀请访客」
  → 填写访客姓名、身份证号、来访时段、（可选）手机号
  → 勾选「已告知访客并取得其同意」
  → 提交
       ↓
一级审批自动通过（邀请人即一级审批人）
       ↓
配置为一级审批 → 直接「已通过」→ 生成凭证 → 下发大门设备
配置为二级审批 → 进入「待二级审批」→ 二级通过 → 生成凭证 → 下发
       ↓
员工收到「已下发」提示，可转告访客
       ↓
访客无需任何操作，到门口刷身份证即可进入
```

**约束**：代邀有效期最长 7 天；邀请人离职或停用时不可代邀。

### 5.4 场景四：现场登记（全程访客自助）

```
访客到达大门，看到张贴的登记二维码
  → 用微信扫码 → 打开本园区小程序
  → 小程序识别为"现场登记"场景，直接展示登记表单
       填写：姓名、手机号、身份证号、访客类型、被访人手机号、时段、（选填）车牌、事由、同行人
  → 提交 → 生成预约单，进入审批链（与自约相同）
  → 页面显示审批进度与预计等待
  → 被访人通过 → 授权下发（实时）→ 页面提示"可刷证进入"
  → 访客刷身份证进入
```

**保安全程只做三件事**

| 时点 | 保安动作 |
|---|---|
| 访客到门口不知所措 | 指引："请扫门上的二维码，填写一下信息" |
| 访客手机没电 / 没带手机 | 引导其使用**门卫室访客自助终端**（同一套页面，大屏自助完成） |
| 访客等太久 | 在「自助登记待处理」列表点「催办」 |

**保安不做的事**（系统层面即无此入口）

- 不读卡、不录入任何访客信息
- 不代填、不代提交
- 不审批、不代审批

**无手机访客的处理**

```
访客无手机或不会操作
  → 保安指向门卫室的访客自助终端（电脑全屏页面）
  → 访客自己在屏幕上填写并提交
  → 与手机扫码完全相同的流程与审批链
  → 保安仅协助切换页面，不参与填写
```

**凭证不可用时的兜底**

授权已通过，但访客手机没电 / 二维码扫不出 / 证件消磁：

```
保安在「在访/待通行」列表中确认该访客已有有效授权
  → 点「远程开门」→ 选择原因（手机没电 / 码扫不出 / 证件消磁）
  → 门开，记录开门人与时间
```

**禁止**：对未获得授权的访客开门。

> **重要提示**：系统不提供保安代审批、也不提供保安代登记。审批人未处理时，访客只能等待。此限制需客户书面确认。

### 5.5 场景五：到访与通行

**访客（携带身份证，主路径）**

```
访客到达大门
  → 在【入口设备】刷身份证
  → 设备读取证件信息，比对现场照片与证件照（人证核验）
  → 检查是否在可通行名单中、是否在有效时段内
  → 通过 → 门开
  → 不通过 → 门不开，屏幕提示原因
  → 系统记录：时间、人员、结果、分值、抓拍，方向＝进场
```

**访客（未携带身份证，二维码路径）**

```
访客到达大门【入口设备】，发现未带身份证
  → 打开手机端「我的预约」→ 预约详情
  → 页面自动展示动态二维码，并显示倒计时（60 秒）
  → 同行人跟随主访客一同到达闸口
  → 将二维码对准入口设备扫码口
  → 设备将二维码内容实时提交平台校验
       校验项：签名有效 / 未过期 / 预约有效 / 门点匹配 / 是否在授权时段内
  → 通过 → 门开；主访客与全部同行人一并记录进场
  → 不通过 → 门不开，屏幕提示原因（过期 / 无授权 / 网络异常）
  → 二维码在 60 秒内可重复使用（进出各刷一次也够用）
```

**关键约束**

| 约束 | 说明 |
|---|---|
| 有效期 | 60 秒，到期页面自动刷新新码 |
| 可重复使用 | 60 秒内可多次通过，适合进出同一扇门 |
| 一人带全队 | 主访客扫一次码，主访客与全部同行人一并放行 |
| 依赖网络 | 校验必须实时联网，断网时不可用 |
| 不做人证核验 | 二维码属凭证通行，身份真实性由审批环节背书 |

**访客（离场）**

```
访客离开
  → 在【出口设备】刷身份证 或 出示二维码扫码
  → 平台校验授权与时段
  → 通过 → 门开，记录离场时间
  → 不通过（已过期/已撤销）→ 仍开闸放行，标记"异常离场"并告警
  → 主访客离场时，同行人一并记录离场
```

**员工**

```
员工到达任一门口
  → 设备摄像头识别人脸
  → 与名单中的人脸比对
  → 通过 → 门开
  → 不通过 → 门不开
  → 员工联系保安，保安核实工号后远程开门
  → 系统记录：时间、人员、结果、分值；人工开门另记操作人
```

### 5.6 场景六：离场与收尾

| 时点 | 动作 |
|---|---|
| 访客离开 | 在**出口设备**刷身份证或扫码，记录离场时间；识别失败仍放行并标记异常 |
| 同行人离开 | 随主访客一同记录离场；单独提前离开时由保安手工签离 |
| 时段结束 | 预约单置为"已过期" |
| 时段结束后 4 小时未签离 | 自动签离，标记"异常离场" |
| 时段结束后 7 天 | 从门口设备名单中移除该访客 |
| 抓拍照片产生后 30 天 | 自动删除照片，保留记录 |
| 通行记录产生后 12 个月 | 归档或删除 |

### 5.7 异常场景

#### 5.7.1 审批超时

```
审批任务超过催办时间（默认 30 分钟）
  → 系统发送一次催办提醒
  → 仍无处理 → 继续等待（不自动通过、不自动转办）
  → 保安可手动催办（每分钟最多 1 次）
  → 访客无法进入
```

#### 5.7.2 网络中断

| 影响 | 表现 | 应对 |
|---|---|---|
| 已授权人员通行 | **不受影响**（设备本地有名单） | 正常刷证/刷脸 |
| 新登记访客 | 无法授权，无法进入 | 保安提示"设备离线"，等待恢复 |
| 员工刷脸失败 | 无法远程开门 | **无法进入**（需恢复网络） |
| 通行记录 | 暂存设备，恢复后自动补传 | 无需人工干预 |

#### 5.7.3 设备故障或断电

| 情况 | 影响 | 应对 |
|---|---|---|
| 设备断电 | 磁吸门失去吸力，门可推开 | 属消防要求；需断电告警 |
| 设备重启 | 短暂无法识别；名单保留 | 自动恢复 |
| 设备恢复出厂 | 名单清空，所有人无法通行 | 系统自动发现并重建（夜间执行） |

#### 5.7.4 审批人变动

| 情况 | 处理 |
|---|---|
| 一级审批人离职 | 待处理任务转给备用审批人；新单不再指派该人 |
| 二级审批人被移出候选池 | 已指派的任务保留，需处理完或由管理员撤销 |
| 审批人手机丢失 | 管理员可转办其任务 |
