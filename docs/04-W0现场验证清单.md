## V1 白名单匹配依据（**最高优先级**）

**为什么验**：若 `certificateMode=2` 的白名单是按**人脸特征**命中而非证件号，则访客必须提前采集人脸照片，"访客不采集人脸"的核心设计全部失效，表结构、小程序流程、合规方案都要改。

**步骤**

1. 设备设置为 `certificateMode=2`（人证+白名单），`faceMode=0`（关闭人脸，避免干扰）
2. 通过平台（或配置工具）下发 **2 个只有证件号、没有任何照片** 的访客：`person_type=1`
3. 用其中一人的身份证刷证
4. 再用一个**未下发**的人刷证

**预期**

| 观察 | 结论 |
|---|---|
| 已下发的证件号刷证 → 开门 | ✅ 按证件号匹配（预期结果） |
| 已下发的证件号刷证 → 不开门 | ❌ 按人脸特征匹配（**方案需变更**） |
| 未下发的证件号刷证 → 不开门 | ✅ 白名单生效 |

**结论**：☐ 按证件号　☐ 按人脸特征　☐ 其他：________

## V2 固件是否支持在线比对接口

**为什么验**：`/api/OnlineComparison` 是 **2022-11-14** 才增加的接口。若固件更老，就没有在线兜底，现场登记完全依赖实时名单下发。

**步骤**

1. 记录固件版本：________
2. 配置工具里查找「在线比对地址 / 比对模式」设置项
3. 若存在：填入 `https://<测试域名>/open/device/v1/compare/online`，用任意方式触发一次识别，抓包或看服务端日志是否有请求
4. 若不存在：确认是否可升级固件（向厂商索要升级包与升级方式）

**结论**：☐ 支持且可用　☐ 支持但需升级固件　☐ 不支持（只能走本地名单）

## V3 有效期字段是否生效（**安全关键**）

**为什么验**：厂商更新日志写明 *2022-07-21 设备修复了人员有效期*。若固件更老，`throughDateTo` 被忽略 → **访客名单永不过期，离职/过期人员可长期进入**，这是安全事故级问题。

**步骤**

1. 下发一个访客，设置 `throughDateFrom = 昨天`、`throughDateTo = 昨天`（已过期）
2. 刷该访客身份证
3. 再下发一个访客，`throughDateTo = 明天`，刷证对照

**预期**

| 观察 | 结论 |
|---|---|
| 过期的人不开门、未过期的人开门 | ✅ 有效期生效 |
| 两人都开门 | ❌ 有效期未生效（**必须平台侧兜底 + 尽快升级固件**） |

> 注意：日期格式必须是 `yyyy-MM-dd`，且**日期后面带一个空格**，否则可能解析失败。

**结论**：☐ 生效　☐ 未生效　☐ 部分生效（说明：________）

## V4 本地名单与在线比对能否混合

**为什么验**：决定"现场登记时名单还没下发完，访客能否先被放行"这条兜底路径是否存在。文档看是全局二选一的模式切换。

**步骤**

1. 设备配置为**本地名单模式**，下发 A（在名单）
2. 配置在线比对地址，但**不切换**比对模式
3. 用 B（不在名单，但平台在线会返回允许）刷证
4. 观察是否向平台发起了在线比对请求

**结论**：☐ 本地不中会自动转在线（有兜底）　☐ 严格二选一（无兜底）　☐ 未测出

## V6 二维码模式：在线校验是否可用

**为什么验**：访客未带身份证时依赖 60 秒动态二维码，**动态码无法预下发到设备**，只能由设备实时上报平台校验。因此必须确认设备支持"在线二维码"模式，且该模式不影响刷证/刷脸。

**步骤**

1. 在设备配置中查找「二维码识别方式」设置项：☐ 有 ☐ 无
2. 将二维码识别方式设置为**在线校验**，填入平台校验地址
3. 用手机生成一个任意内容的二维码（长度 ≥16、非纯数字）
4. 扫描，观察平台是否收到请求：☐ 收到 ☐ 未收到
5. 平台返回"允许"→ 门是否打开：☐ 开 ☐ 不开
6. 平台返回"拒绝"→ 门是否保持关闭：☐ 关闭 ☐ 打开
7. **关键**：在二维码在线模式下，再刷一次身份证 / 刷一次员工人脸，确认仍能正常通行

**预期**

| 观察 | 结论 |
|---|---|
| 平台收到码内容并能返回放行 | ✅ 动态二维码方案可行 |
| 在线二维码开启后刷证/刷脸仍正常 | ✅ 两种通行方式可共存 |
| 开启在线二维码后刷证/刷脸失效 | ⚠️ 需二选一，动态二维码与断网名单冲突 |

**结论**：☐ 支持在线且可共存　☐ 支持但需二选一　☐ 不支持在线二维码

> 若为"需二选一"，则必须让客户决策：**要么保留断网可用（放弃动态二维码），要么采用动态二维码（断网时只能刷证）**。

## V8 入口/出口双设备的方向配置

**为什么验**：客户要求进场与离场分别记录，并由大门入口与出口各一台设备实现。需确认设备的方向参数可靠、两台设备可独立归属同一门点。

**步骤**

1. 查看两台设备参数中的 `inout`（出入方向）配置项：☐ 有 ☐ 无
2. 将入口设备设为"入口"、出口设备设为"出口"
3. 在入口设备刷证，观察上报记录中的方向字段：________
4. 在出口设备刷证，观察上报记录中的方向字段：________
5. 确认两台设备是否可绑定到**同一门点**（同一区域）
6. 确认出口设备是否支持"未在授权名单内仍可放行"的配置（用于异常离场场景）

**预期**

| 观察 | 结论 |
|---|---|
| 两台设备方向字段不同且稳定 | ✅ 平台可直接按设备方向记进出 |
| 方向字段固定为同一值 | ⚠️ 需按设备归属判定方向（平台侧兜底） |
| 出口设备无法配置放行策略 | ⚠️ 异常离场需保安远程开门兜底 |

**结论**：☐ 设备方向可靠　☐ 需平台按设备归属判定　☐ 其他：________

> 若出口设备存在"识别失败即不放行"的硬逻辑，必须在验收前确认应急开门方式，否则人员可能被滞留在园区内。

**若 V1 为「按人脸特征」**：立即暂停开发，重新评估访客照片采集方案与合规方案。
**若 V3 为「未生效」**：平台必须增加「有效期兜底」——在终审通过时按有效期计算删除任务，到期主动 `delete_person`，且不得依赖设备自行过期。
