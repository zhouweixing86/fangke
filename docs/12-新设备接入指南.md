# 新设备接入指南（换机预埋）

> 版本 v1.0 ｜ 2026-11-16
> 背景：现用设备 **YC-P208 / C978GH**（RV1109，局域网 8091 协议）标称工作温度下限 −20 ℃，园区冬季会超出，需更换机型。
> 本文说明**换设备时平台侧什么不用动、设备侧必须满足什么、怎么在 10 分钟内验完**。
> 相关：[06 局域网 HTTP 协议](./06-设备对接协议-局域网HTTP.md)、[07 云对接协议](./07-设备对接协议-RV1109云对接.md)、[09 架构](./09-开发计划与技术架构.md)、[11 接口契约](./11-接口详细契约.md)

---

## 1. 平台与设备之间只有 12 个「语义能力」

业务代码（预约、审批、下发、签到、保安工作台）**只依赖语义能力**，不依赖任何具体报文。
新设备只要能覆盖这些能力，业务与前端零改动；覆盖不了的能力，平台会明确返回 `4006` 并说明缺哪一项。

| # | 能力 | 平台用途 | 缺失后的影响 | 现机（8091） |
|---|---|---|---|---|
| 1 | `PERSON_UPSERT` | 审批通过后把人加进设备名单（访客带证件、员工带照片） | **主链路不可用**，无法授权通行 | ✅ 已验证 |
| 2 | `PERSON_REMOVE` | 撤销授权、过期清理把人从设备删除 | 只能靠设备自身有效期兜底，撤销不及时 | ✅ 已验证 |
| 3 | `PERSON_LIST` | 对账（平台期望 vs 设备实际） | 无法对账，异常名单发现不了 | ✅ 已验证 |
| 4 | `PARAM_READ` | 读心跳地址、比对模式、进出方向等参数 | 无法核对设备配置 | ✅ 已验证 |
| 5 | `PARAM_WRITE` | 写心跳/回调地址、`Comparison` 等（取全量→改→回写） | 新设备需人工在屏幕上配置 | ✅ 已验证 |
| 6 | `DOOR_OPEN` | 保安/管理员远程开门 | 只能现场手动开门 | ✅ 已验证 |
| 7 | `SCREEN_MESSAGE` | 屏幕提示（≤14 汉字，如「请到前台登记」） | 交互提示降级 | ✅ 已验证 |
| 8 | `VERSION_READ` | 固件版本采集、自检 | 只能人工登记 | ✅ 已验证 |
| 9 | `PERSON_CLEAR` | 换机/重置时清空名单 | 需人工逐条删 | ✅ 已验证 |
| 10 | `TIME_SYNC` | 校时（设备时钟漂移会让有效期判定错位） | 靠 NTP 或人工校时 | ✅ 协议支持 |
| 11 | `FACE_PHOTO` | 员工/访客照片随名单下发（`register_base64`） | 员工只能刷证不能刷脸 | ⚠️ 协议支持、**本机人脸下发未验证** |
| 12 | `QR_ONLINE` | 设备扫码后回调平台在线校验动态码 | 未带证件的人无法扫码进门 | ⚠️ 回调链路已通，**二维码识别未验证** |

另有两项**设备主动回调**（不是适配器方法，但新设备必须支持）：

| 回调 | 平台入口 | 说明 |
|---|---|---|
| 心跳 | `/api/device/callback/heartbeat`（兼容 `/heartBeat`） | 30 秒一次；平台靠它判断在线、采集 IP/人数/时钟偏差 |
| 通行记录 | `/api/device/callback/record`（兼容 `/getrecord/`） | 刷卡/刷脸事件；**必须能让平台回 `{"message":"ok","result":0}`** |
| 在线比对 | `/api/device/callback/compare/online` | 动态二维码核验（能力 12） |

## 2. 能力矩阵怎么查、怎么覆盖

### 2.1 查

- 管理后台「设备管理 → 自检」，或
- `GET /api/admin/device/{id}/capabilities` →

```json
[
  {"name":"PERSON_UPSERT","label":"新增/更新名单","supported":true,"byAdapter":true},
  {"name":"FACE_PHOTO","label":"人脸照片下发","supported":false,"byAdapter":false}
]
```

`byAdapter` 是**协议层**声明（新适配器写的），`supported` 是**这台机器**实际可用（叠加了设备档案覆盖）。

### 2.2 覆盖（单台差异）

`device.capability` 列（JSON，可空）支持两种写法，用于「同一型号里这台机器没接读卡器/没装人脸」这类差异：

```json
{"disable": ["FACE_PHOTO", "SCREEN_MESSAGE"]}
{"only": ["PERSON_UPSERT", "PERSON_REMOVE", "PERSON_LIST"]}
```

> 裸数组 `["PARAM_READ"]` 等价于 `only`。写错 JSON 或写了不认识的能力名只会被忽略并打日志，不会影响主流程。

## 3. 自检（换机后第一件事）

`POST /api/admin/device/{id}/selfcheck`（后台「设备管理 → 自检」按钮），返回：

```json
{
  "deviceSn": "NEW-DEVICE-001",
  "model": "YC-P208-NEW",
  "channel": "LAN",
  "checkedAt": "2026-11-16 15:02:11",
  "status": "WARN",
  "items": [
    {"key":"capability","label":"能力覆盖","status":"OK","detail":"名单下发所需能力齐备：[PERSON_UPSERT, PERSON_REMOVE, PERSON_LIST]"},
    {"key":"channel","label":"设备通道","status":"OK","detail":"通道 LAN 已解析到适配器 LanHttpAdapter"},
    {"key":"version","label":"固件版本","status":"OK","detail":"model=... firmware=..."},
    {"key":"params","label":"参数读取","status":"WARN","detail":"缺少平台依赖的参数字段：[heartBeatUrl]"},
    {"key":"persons","label":"名单读取","status":"OK","detail":"设备当前 0 人（容量 500）"}
  ],
  "capabilities": [ /* 见 §2.1 */ ]
}
```

判定口径：

| 结论 | 含义 | 处理 |
|---|---|---|
| `OK` | 能力齐、通道通、参数关键字段全 | 可进入业务联调 |
| `WARN` | 能跑但需人工确认（参数缺字段、名单接近容量） | 按 detail 找厂商确认字段名 |
| `FAIL` | 主链路不可用（缺名单能力、连不上、版本/参数读不到） | 先解决，不要进入联调 |

> **现机实测（2026-11-16，YC-P208）**：自检结论 `OK`。
> 注意参数里**没有** `heartBeatUrl` 这种“整条 URL”字段，实际是 `heartBeatIp` / `platformIp` 分开配；
> 心跳/回调的**路径**由平台在设备上配置（见 docs/08）。换设备时字段名大概率不同，自检会以 `WARN` 点出缺哪几个字段，
> 照着新协议把它们补进 `DeviceSelfCheckService#REQUIRED_PARAMS` 即可。

## 4. 接入步骤

### 第 0 步：没有设备也能先跑通（Mock 通道）

`device.channel = MOCK` 时使用内置模拟设备（`MockDeviceAdapter`）：名单存内存、开门/提示只打日志，**全能力可用**。
用途：前端与业务流程联调不等硬件；新适配器写完后与它做行为对拍。

```sql
UPDATE device SET channel = 'MOCK' WHERE device_sn = 'MOCK-001';
```

### 第 1 步：向厂商要资料（缺一项就别开工）

| # | 资料 | 为什么必须要 |
|---|---|---|
| 1 | 完整协议文档（含报文样例、错误码、字段含义） | 806 行报文的字段语义靠猜必错 |
| 2 | **名单接口的日期格式**（是否要求 `yyyy-MM-dd` 带尾随空格） | 现机不带尾空格会被判参数错 |
| 3 | 名单接口 `usertype` 取值表 | 现机文档写 `visitor` 实测不落库，需 `white` |
| 4 | 名单容量、单批上限、照片格式/大小限制 | 决定分批与压缩参数 |
| 5 | 心跳/记录回调的**报文结构**与**应答格式** | 记录不按格式回 `{"message":"ok","result":0}` 会重推 |
| 6 | 设备口令/鉴权方式（是否走 body `password`） | 平台要能自动下发，不能全靠人工 |
| 7 | 二维码能力说明（在线比对 or 本地名单） | 决定 M7 是否可用 |
| 8 | 人脸下发要求（分辨率、格式、是否需要算法包） | 决定员工刷脸是否可用 |
| 9 | 工作温度、防护等级、供电/网口规格 | 采购与安装 |

### 第 2 步：写适配器（约 1 天）

新建 `device/adapter/XxxAdapter.java`，实现 `DeviceAdapter`：

```java
@Component
public class NewVendorAdapter implements DeviceAdapter {

    @Override
    public boolean supports(Device.Channel channel) {
        return channel == Device.Channel.LAN_V2;   // 新增通道值，避免和现机混用
    }

    @Override
    public Set<DeviceCapability> capabilities() {
        // 如实声明，不要“先全开” —— 平台靠它给现场提示
        return EnumSet.of(PERSON_UPSERT, PERSON_REMOVE, PERSON_LIST,
                PARAM_READ, PARAM_WRITE, DOOR_OPEN);
    }

    @Override public void upsertPerson(Device d, PersonPayload p) { /* 报文映射 */ }
    // ...其余方法
}
```

约定（必须遵守，否则会出现难排查的问题）：

1. **失败要抛 `DeviceException`**（带 `ErrorCode`），不要返回 null 或吞异常；网关靠它决定是否重试。
2. **参数下发必须「取全量 → 合并 → 回写」**，避免固件把未传字段重置为默认值。
3. **不要绕过 `DeviceGateway`**：同一台设备的指令必须串行（批内 `totalnum/currentnum` 有顺序语义）。
4. **设备日期用 `DeviceDateFormats`**，新格式要求写进 `docs/06` 的“接口↔BR 规则”对照表。
5. 能力缺失时**不要自己编错误码**，交给 `DeviceCapabilityService`（4006）。

### 第 3 步：建档案 + 自检 + 五条主链路验收

```sql
-- 新设备入档（旧机先停用，别直接改旧档案，便于回滚）
UPDATE device SET status = 0 WHERE device_sn = 'T77R781116ZS';
INSERT INTO device (device_sn, mac, device_name, model, gate_id, direction, channel, ip, port, status)
VALUES ('<新SN>', '<新MAC>', '大门入口', '<型号>', 1, 1, 'LAN_V2', '192.168.x.x', 8091, 1);
```

> **轮询式终端（`channel=PULL`）不用手工 INSERT**：首次心跳会自动登记，
> 但会落在**「待分配」门点**，必须再走一次 `PUT /api/admin/device/{id}`（后台设备页「档案」）
> 分配到真实门点，否则该门点的访客名单不会下发到这台设备。详见 [14 设备协议](./14-设备协议-新终端HTTP轮询版.md) §10.2。

验收五条（对应 docs/11 §5 与 09 §10 的已验证项）：

| # | 链路 | 判定 |
|---|---|---|
| 1 | 心跳 30 秒一次 → 设备列表「在线」，IP/人数/时钟偏差入库 | 后台在线状态变绿 |
| 2 | 员工导入 → 照片上传 → 名单出现在设备 | 设备屏幕/名单接口能查到 |
| 3 | 提交预约 → 审批通过 → 自动下发 → 设备名单出现该人 | 下发批次 `status=1` |
| 4 | 刷证进门 → 通行记录回调 → 后台「通行记录」有记录且照片可见 | 记录 `result=1`，照片可预览 |
| 5 | 撤销授权/过期清理 → 设备名单消失 | 设备侧查不到 |

再加一条**能力项**：`FACE_PHOTO` 与 `QR_ONLINE` 如果新设备声称支持，必须单独验证，不能只看自检绿。

### 第 4 步：切换与回滚

- 平台的 `person_device_state`（平台期望 vs 设备实际）按 `device_id` 存，旧设备记录停用即可，不需要清库。
- 旧设备 `status=0` 后，所有下发/对账都不再选它；回滚只需把新设备 `status=0`、旧设备 `status=1`。
- 新设备首次接入建议先跑一次「对账」，确认平台不会误删设备存量人员（现机就踩过：首次对账删掉了测试机上的历史人员）。

## 5. 现机踩过的坑（新设备必须逐条复验）

| # | 坑 | 现机结论 | 新设备怎么确认 |
|---|---|---|---|
| 1 | 名单日期必须 `yyyy-MM-dd` + 尾随空格 | 不带空格报文被判参数错 | 用一条测试数据看返回 `result` |
| 2 | `usertype=visitor` 返回成功但不落库 | 必须用 `white` | 加完立刻用名单接口回查 |
| 3 | `platformEnable` 在两个接口语义相反 | 心跳开关 0 为开 | 写参数后回读确认 |
| 4 | `Comparison=1` 指向厂商云，无外网时刷卡静默失败 | 必须改 0（本地名单比对） | 断外网刷一次卡 |
| 5 | 内外网模式 `intranetSetting` 只适用 702K | 对本机无效 | 别在这上面浪费时间 |
| 6 | 记录回调不回指定应答会重推 | 必须 `{"message":"ok","result":0}` | 看平台日志是否有重复事件 |
| 7 | 身份证读卡依赖外网 | 本机无法离线读证 | 新设备要明确问：读证是否离线可用 |

## 6. 平台侧不用改的清单（给项目经理）

换设备**不影响**以下内容，不需要重做需求、不需要改表结构：

- 数据模型（33 张表）、审批流、预约规则、有效期口径（预约当天 00:00–23:59）
- 管理后台 8 个页面、保安工作台
- 照片存储（MinIO）、加密与脱敏、审计
- 已完成的 5 条主链路业务逻辑

需要改的只有：**新增一个适配器类 + 一行设备档案（channel/型号/SN/MAC/IP）+ capability 覆盖（如有）**。

> 若新设备只支持云对接（无本地 HTTP），则走 `CloudMqttAdapter`（对应 docs/07），平台侧同样只换适配器；但**云通道意味着名单/记录要经厂商云中转**，客户数据合规需提前确认。
